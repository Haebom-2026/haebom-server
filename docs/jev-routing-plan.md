## 0. 한 줄 요약

어르신의 말을 **jev(고르기 전용 모델)로 지도에 있는 "어느 앱의 어느 목표"인지 두 단계로 고르고**, 지금 화면에서 그 목표의 도착지까지 **검증된 이동 연결선**이 있으면 Claude 없이 지도대로 안내한다. 길이 없거나, 화면이 조금이라도 어긋나거나, 민감한 행동이 나오면 지금처럼 Claude가 안내하거나 멈춘다. 명령이 끝나면 **Opus가 기록을 검토하고 서버가 다시 확인한 길만 지도에 더한다**.

**안전 분류(민감도·사기 의심)는 jev와 상관없이 늘 따로 돈다.** jev의 결과는 민감도를 올리는 데만 쓰고 내리는 데는 쓰지 않는다.

```
어르신 말 ─┬─▶ 안전 분류 (규칙 + Claude, 늘 돎) ──────────────▶ 민감도·사기 의심
           └─▶ jev 1단계: 앱 → 후보 앱 순서 (최대 3개)
               jev 2단계: 후보 앱들의 목표 (동시에)
               폰: 후보 중 깔린 첫 번째 앱 → 서버에 고정 (설치 앱 목록은 폰 밖으로 안 나감)
   ├─ 검증된 목표 + 도착지까지 검증된 이동 ─▶ 【지도 안내】 화면마다 엄격한 페이지 맞추기 → 이동 한 단계
   │        ├─ 도착 → 목표의 끝 단계 (확인할 수 있는 것만, 민감하면 멈춤)
   │        └─ 화면이 어긋남·확인 못 함 ─▶ 그 자리부터 Claude
   ├─ 목표는 있는데 길 없음 ─▶ 【Claude 안내】 (route를 알려 줌)
   └─ 실패 (해당 없음·애매함·오류) ─▶ 【Claude 안내】 지금 흐름 그대로
                    │
          명령이 끝나면 (앱의 끝 신호 + 마지막 화면)
                    ▼
     【Opus 검토】 비동기
       ① 정말 성공했나 (마지막 화면 근거)  ② 이동과 끝 단계로 나눔  ③ 개인 값 → 슬롯  ④ 기존 목표인가
                    ▼
     【서버 확인】 행동 기록과 맞나, 민감한 행동이 이동에 섞였나, 화면 속 지시가 섞였나
                    ▼
     지도에 반영 (8장): 후보 → 서로 다른 어르신·다른 날 성공이 쌓이면 검증됨. 새 목표는 사람 확인
```

## 1. 왜 하나

| 문제                                                                                                   | 이 구조가 푸는 방법                                                                   |
| ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| Sonnet guide는 요청마다 약 $0.0055(캐시 없으면 약 $0.02), 1.8~4.1초                                    | 검증된 길이 있는 목표는 화면마다 Claude를 부르지 않음                                 |
| 어르신 말이 제각각이라 캐시 키로 못 씀 ("등본 떼 줘" / "주민등록 등본 발급 받고 싶어" / "정부24 등본") | jev가 모두 `gov24.resident_copy` 하나로 모음 → 길을 목표 단위로 모을 수 있음          |
| 앱·목표를 사람이 미리 다 적을 수 없음                                                                  | 실제 사용에서 Claude가 성공한 안내를 Opus가 검토해 **지도에 더함**                    |
| 목표는 다른데 길은 거의 같음 (화면 밝게 / 어둡게)                                                      | 이동은 **모든 목표가 같이 쓰는 연결선**, 목표에는 도착지와 끝 단계만 둠               |
| 글을 만드는 모델은 엉뚱한 값을 낼 수 있음                                                              | jev는 **목록 안에서 고르기만** 하고 후보별 확률을 줌 → 애매하면 확실하게 넘길 수 있음 |

- 비용을 아끼는 곳은 **화면마다 부르는 guide**다. 명령 시작 때 한 번 하는 안전 분류는 Claude를 그대로 부른다 (v0.2에서는 jev가 성공하면 건너뛰려 했으나, 안전 분류를 라우팅에 기대면 위험도를 낮게 볼 수 있어 되돌림: 14장 1)

| 시험                        | 그대로 쓸 때             | 기준을 두면                                       |
| --------------------------- | ------------------------ | ------------------------------------------------- |
| A. 말 → 앱                  | 98% (63/64)              | 1등 ≥ 0.5: 97% 받아들임, 그중 **100%** 정확       |
| B. 말 + 앱 → 목표           | 98% (42/43)              | 1등 ≥ 0.7·차이 ≥ 0.3: 93% 받아들임, 그중 **100%** |
| C. 화면 + 할 일 → 누를 노드 | 42% (Claude와 같은 버튼) | 1등 ≥ 0.9: 18%만 받아들임 → **쓰지 않음**         |

→ **앱·목표 고르기(A·B)에만 쓴다.** 화면에서 누를 버튼은 지도의 `targetText` 또는 Claude가 정한다.

\* 11개 시험에서는 새 말 상당수의 정답이 '해당 없음'이라 받아들임이 낮다.

- **개수는 문제가 아니다**: 앱 60개에서도 시간이 같고, 24개 목표 안의 비슷한 쌍을 모두 맞힘 → 2단계(앱 하나의 목표만 물음)가 잘 버팀
- **틀린 것은 같은 역할 앱 사이**: "트로트 틀어 줘" → 멜론, "임영웅 콘서트 검색해 줘" → 네이버. 같은 역할 앱을 허용해 다시 채점하면 앱 30·60개 모두 **받아들인 것 중 100%** (4.3에서 역할로 묶음)
- 같은 역할 앱이 여럿이면 확률이 나뉘어(멜론 0.44 + 지니 0.20 …) 1등이 0.5 아래로 → 받아들임이 86~89%로 줄어듦 (안전하게 Claude로 넘어감) → 역할 합계로 판정 (4.2)
- **"배달의민족 깔아 줘" → 배달의민족 앱 0.90** (받아들였는데 틀림). 1단계 지시문에 "앱 이름이 있어도 깔기·업데이트·지우기면 Play 스토어"를 넣으니 Play 스토어 0.90으로 고쳐짐 (3.4)
- 한계: 새 말 34개와 정답은 직접 씀. 설치 앱으로 좁히는 효과는 반영하지 않음 (2.3에서 잼)

### 2.3 후보를 보내고 폰이 고르기 (2026-11-27)

4.3·4.4의 방식 시험. 서버는 지도 앱 60개 전체로 1단계를 고르고, 역할로 묶어 후보 앱을 최대 3개 순서대로 낸 뒤, 후보 중 목표가 있는 앱의 2단계를 동시에 부른다. 폰은 설치 앱이 무작위로 다른 가상 폰 30대(앱마다 30%, 유튜브·카톡 95%, 기본 앱 100%)가 후보 중 깔린 첫 번째 앱을 고른다. 말 98개, $0.023.

| 항목                                                   | 결과                             |
| ------------------------------------------------------ | -------------------------------- |
| 서버가 후보를 낸 89개 중 정답 앱이 후보 안에 있음      | **100%**                         |
| 폰이 깔린 첫 번째 후보를 고름                          | 95.7%                            |
| **+ 말한 앱이 분명하면(1등 ≥ 0.7) 그 앱만 후보 (4.3)** | **99.6%**                        |
| 2단계 목표 (정답 앱)                                   | 그대로 100%, 받아들인 것 중 100% |
| 명령 하나 고르는 시간 (1단계 + 2단계 동시)             | 중앙값 0.94초, 최대 1.15초       |
| 명령당 비용                                            | $0.00012                         |
| 2단계를 동시에 부른 앱 수                              | 평균 0.5개, 최대 1개             |

- 95.7%에서 틀린 것은 거의 모두 **말한 앱이 폰에 없어서 같은 역할 앱으로 바꾼 것**: 카톡 보내 줘 → 문자, 멜론에서 → 유튜브, 넷플릭스 → 유튜브, 쿠팡에서 → 11번가, KTX → SRT → 4.3에 "말한 앱이 분명하면 바꾸지 않고 설치를 물음" 규칙을 둠
- 남은 틀림 2개는 역할 설계 문제: 크롬을 '검색' 역할에 넣음(→ 크롬은 따로), 네이버 지도(0.69)가 '지도'·'대중교통' 두 역할이라 합계가 큰 대중교통 쪽 지하철 앱으로 바뀜(→ 여러 역할 앱의 역할 고르기는 4.2 주의 참고)
- Claude로 넘어간 것(7개: "은행에 돈 보내야 돼", "설치해 줘" …)과 하려는 일을 물은 것(2개: "임영웅 찾아줘" 음악 0.29 / 영상 0.26)은 모두 안전한 쪽
- 한계: 가상 폰의 설치 확률·말 34개·역할 묶음은 직접 정함. 실제 폰에서 패키지 확인이 되는지는 앱 팀 확인 필요 (4.4)

| 항목                               | 처음 지도 (앱 10개) | 큰 지도 (앱 59개) |
| ---------------------------------- | ------------------- | ----------------- |
| 정답 앱이 후보 안에 있음           | 97.2%               | 100%              |
| 가상 폰이 깔린 첫 번째 후보를 고름 | 100%                | 99.9%             |

- R1 코드는 v0.3 판정 순서(4.2)와 다르다: 지금은 '해당 없음'이 1등이어도 다른 앱이 0.5 이상이면 후보를 낸다. R1.1에서 고친다

## 3. 지도

지도는 코드가 아니라 **데이터**다. 사용하면서 늘어나므로 배포 없이 바뀌어야 한다. 처음 목록(앱 10개 × 목표 2~6개)은 손으로 넣고(`origin: seed`), 그 뒤는 Opus 검토로 늘어난다(`origin: learned`).

```
역할 (음악, 검색, 은행 …)
 └ 앱 (유튜브, 멜론 …)            ← jev 1단계 후보
    └ 목표 (도착지 + 끝 단계)      ← jev 2단계 후보
페이지 ──이동 연결선──▶ 페이지     ← 모든 목표가 같이 쓰는 이동 (부작용 없는 것만)
```

### 3.1 역할과 앱

```ts
// 역할 (제안)
{ id: "music", name: "노래 듣기", defaultApp: "youtube", sensitive: false }
{ id: "bank",  name: "은행",      defaultApp: null,      sensitive: true  }

// 앱 (제안)
{ id: "melon",   name: "멜론",   aliases: ["멜론"],         desc: "노래 듣기, 음원 검색",    roles: ["music"],          packages: ["com.iloen.melon"] }
{ id: "youtube", name: "유튜브", aliases: ["유튜브", "유투브"], desc: "영상·노래·공연 찾아보기", roles: ["video", "music"], packages: ["com.google.android.youtube"] }
```

- `roles`: 같은 일을 대신할 수 있는 앱끼리 묶는다 (4.3). 한 앱이 여러 역할일 수 있다 (유튜브 = 영상·음악). 웹 브라우저처럼 무엇이든 되는 앱은 역할에 넣지 않고 따로 둔다 (2.3)
- `aliases`: 어르신이 앱 이름을 **실제로 말했는지** 판정하는 데 쓴다 (4.2). jev 확률만으로는 "말했다"는 증거가 되지 않는다 (14장 10)
- `defaultApp`: 습관으로 못 정할 때 앞에 세우는 앱. 보호자가 바꿀 수 있게 한다. 민감한 역할은 두지 않는다
- `packages`: 폰이 깔려 있는지 확인할 때 쓴다 (4.4)

### 3.2 목표 = 도착지 + 끝 단계

```ts
// 목표 하나 (제안)
{
  id: "settings.brightness_down",     // 한 번 쓴 id는 지운 뒤에도 다시 쓰지 않음
  version: 2,                         // 설명·민감도·슬롯·끝 단계가 바뀌면 올림
  app: "settings",
  name: "화면 어둡게",                 // 어르신께 물을 때 보여 주는 짧은 이름
  desc: "화면을 더 어둡게 (눈부심 줄이기)",   // jev 후보 설명
  level: "L0", category: "settings",  // 민감도 (안전 분류를 올리는 데만 씀, 5.1)
  approvalAction: null,               // S3 승인 action (있으면)
  slots: [],                          // 필요한 값. 예: youtube.search → ["query"]
  arrive: [{ page: "pg_brightness", pkgVersions: ["15.0"] }],   // 도착 페이지 (앱 버전마다)
  finish: [                           // 도착한 뒤 이 목표만 하는 단계 (1~3개)
    {
      action: "swipe_left", targetText: "밝기",
      verify: "none",                 // 끝났는지 화면으로 확인하는 법: page | node_state | none
      sensitive: false,
    },
  ],
  stopAt: null,                       // 멈춤 단계 번호 (송금·결제·설치·권한·보내기·동의 확인이면)
  status: "verified",                 // candidate | verified | retired
  origin: "learned",                  // seed | learned
}
```

- 밝게 / 어둡게는 `arrive`가 같고 `finish`만 다르다. 이동은 3.3의 연결선을 같이 쓴다
- **끝 단계는 확인할 수 있어야 자동으로 넘어간다** (14장 4). `verify`
  - `page`: 다음 화면이 정해진 페이지면 끝
  - `node_state`: 같은 화면에서 노드 상태(체크됨·선택됨)가 바뀌면 끝 (화면 지문에 상태를 넣는 match@v2 필요, 3.7)
  - `none`: 화면으로 확인할 수 없음 (밝기 막대처럼 값이 화면 글자에 안 나옴) → **지도는 그 단계 앞에서 멈추고 Claude에 넘긴다**. 한 번 안내한 단계를 다시 안내하지 않도록 진행 상태는 서버가 들고 있다 (5.3)
- **안내 문장(`say`)은 저장하지 않는다**. 행동과 글자로 서버가 정해진 틀에서 만든다 ("'{글자}'를 눌러 주세요", "막대를 왼쪽으로 밀어 주세요"). 화면 속 문구가 안내 문장으로 들어가는 길을 막는다 (14장 6)
- 개인 값은 슬롯 자리(`{query}`, `{name}`)로 저장한다. 예: `youtube.search`의 `finish`는 `[검색창에 type {query} (verify: page)]`
- 모든 질문에 **`none`(해당 없음)** 후보를 넣는다
- 목표가 없는 앱(갤러리, 카메라 등)은 `<앱>.open` 하나로 본다 (`arrive` = 앱 첫 화면, `finish` 없음)
- jev 후보에는 `candidate`·`verified` 목표를 모두 넣는다. 다만 **`candidate` 목표의 `level`은 안전 분류에 쓰지 않는다** (5.1)

### 3.3 이동 연결선 (모든 목표가 같이 씀)

```ts
{
  key: "pg_settings_home|tap|디스플레이|pg_display",   // from | action(+dir) | targetText | to
  from: "pg_settings_home",           // 페이지 id (3.7)
  to: "pg_display",
  action: "tap", targetText: "디스플레이",   // swipe면 dir까지 키에 넣음 (반대 방향 밀기를 합치지 않게)
  pkgVersions: ["15.0"],              // 성공이 쌓인 앱 버전. 다른 버전에서는 쓰지 않음
  stats: { elders: 4, days: 3, mapGuided: 30, mapFailures: 1 },
  status: "verified",                 // candidate | verified | retired
  demotedAt: null,                    // 내려간 때. 그 뒤의 새 성공만 다시 셈 (8.3)
}
```

- **연결선은 부작용 없는 이동만 담는다** (14장 2). `tap`은 설치·권한 허용·보내기·결제도 실행할 수 있으므로, 아래 중 하나라도 맞으면 연결선이 될 수 없고 **목표의 `finish`(멈춤 단계 포함)로만** 들어간다
  - 누를 노드의 글자·설명이 민감 단어 목록에 걸림: 설치, 허용, 동의, 보내기, 전송, 결제, 구매, 이체, 송금, 삭제, 탈퇴, 확인, 완료, 등록, 신청 …
  - 출발 화면에 결제·인증·권한 창의 표지가 있음 (금액, 비밀번호 칸, 시스템 권한 창 패키지)
  - Opus가 `sensitive`로 표시
  - 도착 페이지가 출발 페이지와 같음 (화면 안에서 값만 바뀐 것은 이동이 아님)
- 이 검사는 학습 때만이 아니라 **지도로 안내하기 직전에도 지금 화면에 대해 다시** 한다 (5.3)
- **노드 번호는 저장하지 않는다**. `targetText`로 지금 화면에서 다시 찾는다. 같은 글자의 노드가 화면에 둘 이상이면 쓰지 않는다 (Claude)
- 어느 목표를 하다가 성공했든 연결선의 증거로 센다. 밝기를 올리다 성공한 어르신 덕에 "설정 → 디스플레이"가 검증되면, 글자 크기 목표도 그 연결선을 바로 쓴다

### 3.4 중복을 없애는 규칙

| 겹침                                     | 예                                    | 처리                                                                             |
| ---------------------------------------- | ------------------------------------- | -------------------------------------------------------------------------------- |
| 같은 뜻, 이름만 다름                     | 등본 발급 / 등본 떼기 / 등본 출력     | **하나로 합침**. 다른 이름은 `desc`에 넣음                                       |
| 결과가 같고 끝 단계도 같음               | 등본 PDF 받기 / 등본 저장             | 하나로 합침                                                                      |
| 이름은 비슷한데 결과·끝 단계가 다름      | 등본 PDF 받기 / 등본 우편 신청        | **나눔** (v0.2는 합쳤으나 하나의 `finish`로 뜻을 보존 못 함: 14장 12)            |
| **결과는 다른데 길은 같음**              | 화면 밝게 / 어둡게, 글자 크게 / 작게  | **목표는 나누고 길은 같이 씀** (도착지 같음, `finish`만 다름)                    |
| 비슷하지만 정말 다름                     | 등본 / 초본, 송금 / 잔액 조회         | 남기고 `desc`에 **차이를 만드는 말**을 적음. 그래도 애매하면 어르신께 물음 (4.2) |
| 같은 일을 하는 다른 앱                   | 유튜브 / 멜론 / 지니                  | 앱은 따로, **역할로 묶음** (4.3)                                                 |
| 앱 자체에 대한 일 (깔기·업데이트·지우기) | "배달의민족 깔아 줘", "카톡 업데이트" | 그 앱이 아니라 **Play 스토어 목표** (`playstore.install` + 슬롯 `{appName}`)     |

합칠지는 점수 하나로 정하지 않는다 (7.3): jev 점수·1·2등 차이 + 슬롯·민감도·도착지·끝 단계가 맞을 때만 합친다.

### 3.5 저장

- **원본(편집용)**: DynamoDB main 테이블. 목표·연결선·증거를 항목으로 둔다
- **게시본(읽기용)**: 바뀐 것을 모아 **지도 스냅샷**(`map@vN` JSON, S3)으로 게시한다. ai-fn은 스냅샷 하나를 읽어 메모리에 둔다. 서로 다른 세대의 목표·연결선이 섞이지 않는다 (14장 16)
- 명령은 시작할 때의 지도 버전을 `CMD#`에 고정하고, 그 명령은 끝까지 같은 버전으로 안내한다
- **긴급 내리기**: 목표·연결선을 바로 막아야 하면 작은 차단 목록 항목(`MAP` / `BLOCK`)에 넣는다. ai-fn은 이 항목만 1분마다 다시 읽는다 (스냅샷 재게시를 기다리지 않음)

| 엔티티      | PK                | SK                   | 주요 속성                                                           |
| ----------- | ----------------- | -------------------- | ------------------------------------------------------------------- |
| 역할        | `MAP`             | `ROLE#<roleId>`      | name, defaultApp, sensitive                                         |
| 앱          | `MAP`             | `APP#<appId>`        | name, aliases, desc, roles, packages                                |
| 목표        | `MAP`             | `GOAL#<goalId>`      | version, name, desc, level, slots, arrive, finish, stopAt, status   |
| 연결선      | `MAP`             | `EDGE#<edgeKey>`     | from, to, action, targetText, pkgVersions, stats, status, demotedAt |
| 증거        | `EVID#<대상>`     | `<eid>#<commandId>`  | 결과, 날짜 (조건부 Put: 같은 명령을 두 번 세지 않음)                |
| 게시 포인터 | `MAP`             | `PUBLISHED`          | version, s3Key                                                      |
| 긴급 차단   | `MAP`             | `BLOCK`              | goalIds, edgeKeys                                                   |
| 명령 상태   | `CMD#<commandId>` | `META`               | uid, mapVersion, candidates, chosenApp, progress, ttl(+1일) (5.2)   |
| 어르신 선호 | `ELDER#<eid>`     | `PREF#ROLE#<roleId>` | appId, updatedAt (4.3)                                              |

- `PK=MAP` 한 파티션에 목표·연결선이 모이므로 게시 작업이 Query 한 번(페이지 나눔)으로 다 읽는다. 연결선이 수만 개를 넘으면 앱별 파티션으로 나눈다
- 변경은 모두 기록한다 (누가: seed / opus / 사람, 언제, 무엇을). 목표·연결선 단위로 되돌릴 수 있게

### 3.6 지도 만들기

**지도는 실제 사용으로만 자란다**: Claude 안내 → 끝 신호 → Opus 검토 → 서버 확인 → 후보 → 검증됨 (6~8장). 처음엔 지도가 비어 있어도 손해가 없다. 길이 없으면 Claude가 안내하는데, 이것이 지금 동작 그대로다.

| 층     | 어떻게 생기나                                                                                                      | 지금 상태                                                                                |
| ------ | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| 페이지 | 화면이 들어올 때마다 이미 본 페이지인지 판정 (3.7)                                                                 | dev에서 `match@v1`로 저절로 생기고 있음. 지도용 엄격 판정(match@v2)·서비스 저장소가 남음 |
| 연결선 | 앱이 보낸 **실제 행동 기록**(5.2 `lastAction`)으로: `출발 화면 + 행동 + 도착 화면`이 빠짐없이 이어진 것만          | `commandId`·`lastAction`이 없어 아직 못 만듦                                             |
| 목표   | 처음 목록은 손으로 넣고, 그 뒤 Opus가 기존 목표에 붙이거나 새 목표를 제안. **새 목표는 사람 확인 뒤 들어감** (8.2) | 시험용 목록(앱 10개, 큰 목록 59개)만 있음                                                |

- **실제로 누른 것**: 서버는 무엇을 누르라고 했는지만 안다. 앱이 guide 요청에 `lastAction: { stepId, seq, action, text, dir? }`(바로 앞 화면에서 실제 한 행동)를 보내야 연결선을 **실제 행동**으로 만든다. 글자만으로는 중간 화면·뒤로 가기·밀기를 구별하지 못한다 (14장 5)
  - `stepId`: 서버가 안내 응답마다 붙이는 id. 어르신이 안내를 따랐는지 확인하는 데 씀
  - `seq`: 명령 안에서 행동 순번. 빠진 번호가 있으면 그 구간은 학습하지 않음
- **dev 기록을 시간으로 묶어 연결선을 뽑는 것은 하지 않는다**
- **팀 녹화는 시연용으로만**: `scripts/adb-capture`로 흐름을 녹화해 **사람 승인**으로 넣는다(`origin: seed`). 실제 사용에서 실패가 쌓이면 똑같이 내려간다
- 지도가 자라는 것은 **앱이 `commandId`·`lastAction`·끝 신호를 보내기 시작한 뒤**다 (R6). prod 학습은 개인정보 정책이 정해진 뒤 (12장)

### 3.7 지도용 페이지 맞추기 (match@v2)

지금 `match@v1`은 "비슷한 화면 묶기"(디버그 뷰어)로는 충분하지만 **저장된 행동을 다시 쓰기에는 약하다** (14장 3).

| match@v1의 약점                                                  | 지도용으로 바꿀 것                                                                    |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 숫자를 `#`로 바꾸고, 선택·체크 상태를 보지 않음                  | 지문에 노드 상태(체크·선택·켜짐)를 넣음. 숫자 위치는 유지                             |
| 토큰 겹침이라 위치를 보지 않음                                   | 누를 노드의 위치 구간·클래스까지 확인                                                 |
| `similar` 판정 화면의 지문을 페이지에 계속 더함 → 나중엔 `exact` | 지도용 페이지에는 **사람 확인 또는 `exact`로만** 지문을 더함. `similar`는 더하지 않음 |
| 앱 버전을 보지 않음                                              | 페이지·연결선에 앱 버전(`pkgVersions`)을 붙이고, 다른 버전은 쓰지 않음                |

지도 안내는 다음이 **모두** 맞을 때만 한다. 하나라도 아니면 Claude.

1. 지금 화면이 지도 페이지와 `exact` (match@v2)
2. 앱 패키지가 명령에 고정된 앱이고, 앱 버전이 연결선의 `pkgVersions` 안
3. 누를 `targetText` 노드가 화면에 **하나뿐**이고, 클래스·위치 구간이 저장된 것과 같음
4. 3.3의 민감 검사를 지금 화면에 다시 해서 통과

## 4. 고르기 (jev)

### 4.1 두 단계로 묻기

**결정: 앱을 먼저 고르고, 그다음 그 앱의 목표를 고른다 (2단계).** 목표 질문에는 언제나 **고른 앱 하나의 목표만** 들어가서, 앱이 늘어도 목표 후보 수는 앱 하나 분량으로 유지된다 (2.2: 24개 목표에서도 100%).

```
1단계  POST decisions { state: 말, questions: { app: 지도의 앱 전체 + none } }
         └─ 판정 (4.2) → 후보 앱 순서 (4.3). 실패면 route 없음 (안전 분류·Claude 안내는 그대로)
2단계  후보 앱 중 목표가 있는 앱마다 POST decisions { goal: 그 앱의 목표 후보 + none } — 동시에
         └─ 목표가 하나뿐인 앱(<앱>.open)은 건너뜀. 2.3에서 동시 호출은 평균 0.5개, 최대 1개
```

- 1단계 지시문에 **"말에 앱 이름이 들어 있어도 그 앱을 새로 깔기·업데이트·지우려는 말이면 Play 스토어"**를 넣는다 (2.2)
- 서버는 그 폰에 무엇이 깔렸는지 모른다. 깔린 앱 고르기는 폰이 한다 (4.3·4.4)
- 시간: 1단계 + 2단계(동시)로 약 1초 (2.4: 중앙값 0.71초, 최대 1.06초). **안전 분류(Claude)와 동시에** 돌리므로 classify 전체 시간은 둘 중 긴 쪽이다. 두 호출을 합쳐 1.5초가 넘으면 route 없이 끝낸다 (Claude 분류 시간에 더해지지 않음)
- 비용: 명령당 약 $0.00012 (앱 59개)
- 앱 후보가 아주 많아 1단계 정확도가 떨어지면, 역할을 먼저 고르는 단계를 하나 더 둔다 (지금 60개까지는 필요 없음)

### 4.2 받아들이는 기준 (시작값, 10장에서 조정)

**1단계 (앱)** — 위에서부터 처음 맞는 줄. v0.2와 달리 **'해당 없음'과 애매함을 먼저 본다** (14장 10):

| 순서 | 조건                                                                                                                 | 처리                                                                                                                                                            |
| ---- | -------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | jev 오류·시간 초과                                                                                                   | route 없음                                                                                                                                                      |
| 2    | `none` ≥ 1등 앱                                                                                                      | route 없음                                                                                                                                                      |
| 3    | 말에 앱 별칭(`aliases`)이 있음 (**말한 앱**)                                                                         | 그 앱이 1등이면 후보 = **그 앱 하나** (4.3). 1등이 Play 스토어면 `playstore.*` + 슬롯 `{appName}`. 그 밖의 다른 앱이 1등이면 **route 없음** (말과 jev가 어긋남) |
| 4    | 1·2등 역할이 둘 다 0.25 이상, 차이 < 0.2, 두 역할이 같은 1등 앱에서 나온 것이 아님 ("임영웅 찾아 줘": 영상 / 연락처) | **하려는 일을 물음**: 역할 `name`으로 options. 앱 이름을 늘어놓지 않음                                                                                          |
| 5    | 1등 앱 ≥ 0.5                                                                                                         | 후보 = 그 앱 + 1등 앱의 모든 역할에서 같은 일을 하는 앱 (4.3)                                                                                                   |
| 6    | 역할별 확률 합계의 1등 ≥ 0.5 (예: 멜론 0.44 + 지니 0.20)                                                             | 역할 확정 → 후보 = 그 역할 앱 (4.3)                                                                                                                             |
| 7    | 그 밖                                                                                                                | route 없음                                                                                                                                                      |

- "말한 앱"은 jev 확률(v0.2: 1등 ≥ 0.7)이 아니라 **말에 앱 이름이 실제로 있는지**로 정한다. 확률 0.69로 말한 앱이 다른 앱으로 바뀌는 일을 막는다
- 두 역할이 같은 1등 앱에서 나왔으면(유튜브 = 영상·음악) 하려는 일은 갈리지 않았으므로 5번으로 간다 (R1에서 고침, 2.4)

**2단계 (목표)** — 후보 앱마다:

| 결과                                                                 | 처리                                       |
| -------------------------------------------------------------------- | ------------------------------------------ |
| 목표 1등 ≥ 0.7 이고 1·2등 차이 ≥ 0.3, `none` 아님                    | **목표 확정**                              |
| 목표 1·2등이 둘 다 0.3 이상이고 차이 < 0.3 (예: 등본 0.5 / 초본 0.4) | **어르신께 물음** (그 후보 앱의 질문, 4.3) |
| 그 밖 (목표 `none`, 1등 < 0.7)                                       | 목표 없음 → 그 앱에서 Claude 안내          |

### 4.3 후보 앱 순서와 폰의 고르기

서버는 **순서를 매긴 후보 앱(최대 3개)**만 보내고, 폰이 **후보 중 깔린 첫 번째 앱**을 쓴다. 판단 규칙은 서버에 있어 규칙을 바꿔도 앱을 업데이트하지 않는다.

**서버가 순서를 매기는 법**

| 경우                                    | 후보                                                                                                  |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 말한 앱 (4.2 3번)                       | **그 앱 하나**. 없으면 같은 역할 앱으로 바꾸지 않는다 (2.3: 카톡 → 문자, 멜론 → 유튜브로 바꾸면 틀림) |
| 그 밖 (역할로 정해짐, "트로트 틀어 줘") | ① 이 어르신이 평소 쓰던 앱(`PREF#ROLE#music`) ② 역할 기본 앱(`defaultApp`) ③ jev 확률 순              |

- **목표가 약해지는 앱을 앞에 세우지 않는다** (14장 11): 한 후보가 구체 목표(`youtube.search`)를 확정했는데 다른 후보는 목표 없음·`open`뿐이면, 선호·기본 앱이라도 구체 목표가 확정된 후보 뒤로 보낸다. "임영웅 검색해 줘"가 멜론 열기로 줄어드는 일을 막는다

**후보마다 2단계 결과를 따로 싣는다**. 폰이 앱을 고른 뒤 **그 후보의** 결과를 쓴다.

```
candidates[i] = { appId, packages, name, by,
                  goal?:    { id, version, level },              // 목표 확정
                  clarify?: { questionId, say, options[] },      // 이 후보 앱에서 물을 것
                  (둘 다 없으면 목표 없음) }
```

**폰이 하는 일**

| 경우                                 | 처리                                                                                                                                                      |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 깔린 후보가 있음                     | 첫 번째를 고르고 **바로 서버에 알림** (`POST /v1/elder/commands/{commandId}/app`, 5.2). 그 후보에 `clarify`가 있으면 그 질문을 묻고 답을 같은 곳으로 보냄 |
| 말한 앱(후보 하나)이 안 깔림         | "멜론이 없어요. 설치할까요?" → 예면 **새 명령**으로 `playstore.install` (슬롯 `{appName}`)을 classify부터 다시                                            |
| 역할 후보가 하나도 안 깔림           | "노래 들을 앱이 없어요" + 기본 앱 설치를 권함 (예면 위와 같이 새 명령)                                                                                    |
| 확인 불가 (4.4)                      | 설치를 권하지 않는다. 그 후보를 고른 것으로 하고 앱 열기는 Claude 안내에 맡김                                                                             |
| 민감한 역할 (`ask: true`, 은행·결제) | 순서대로 고르지 않는다. **깔린 후보만** 선택지로 보여 주고 묻는다. 고른 결과를 서버에 알림 (서버가 "물어서 고름"을 기록)                                  |

- 어르신 선호는 끝 신호 `done`인 명령의 앱으로만 갱신한다 (6장)

### 4.4 설치 확인은 폰 안에서

설치 앱 목록은 **폰 밖으로 보내지 않는다**. 서버가 보낸 후보 몇 개가 깔려 있는지만 폰이 확인한다.

안드로이드 11부터는 **"이 앱 하나가 깔려 있나?"라고 묻는 것도** 볼 권한이 없으면 "없음"으로 나온다 (`getPackageInfo`, `getLaunchIntentForPackage` 모두). 그래서 폰의 확인 결과는 **세 가지**로 둔다 (14장 15): `installed`(깔림) / `missing`(안 깔림이 확실함) / `unknown`(볼 권한이 없어 모름). `unknown`을 안 깔림으로 다루면 이미 있는 앱의 설치를 권하게 된다.

| 방법                             | 내용                                                                                                                                                                                                                   | 장단점                                                                                                         |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| **A. 런처 intent 선언 (제안)**   | manifest `<queries>`에 `MAIN`/`LAUNCHER` intent를 한 번 선언 → 아이콘이 있는 앱을 볼 수 있음. 코드는 **서버가 보낸 후보만** 확인. 결과는 `installed` / `missing`                                                       | 앱 업데이트 없이 새 앱도 확인. `QUERY_ALL_PACKAGES` 권한은 안 씀. **Play 심사에서 문제없는지 앱 팀 확인 필요** |
| B. 패키지 이름을 manifest에 적기 | 처음 지도(seed) 앱을 `<queries><package>`로 적음. 적은 앱은 `installed` / `missing`, 적지 않은 새 앱은 `unknown`                                                                                                       | 정책상 가장 깔끔. 새로 배운 앱은 다음 앱 업데이트 전까지 `unknown`                                             |
| C. 열 때 확인                    | `unknown` 앱은 열기 단계에서 확인: 명시적 intent로 `startActivity`를 부르고 `ActivityNotFoundException`이면 `missing`. API 33 이상은 `getLaunchIntentSenderForPackage`로 실행 경로를 얻음 (버전별 경로는 앱 팀이 정함) | 볼 권한 없이 됨. 앱이 실제로 열리므로 조용히 확인할 수 없음 → 열기 직전에만                                    |

- **제안**: A. A가 정책상 어려우면 B + C
- 고령자 앱은 접근성 서비스로 동작한다. 접근성 서비스에 이 제한이 다르게 걸리는지는 확인하지 못했다 → 앱 팀이 실제 기기에서 `getPackageInfo`를 시험
- 기기 사용 기록 권한(`PACKAGE_USAGE_STATS`)은 쓰지 않는다

### 4.5 슬롯 (말 속의 값)

jev는 고르기만 하므로 "임영웅", "김철수" 같은 값은 뽑지 못한다.

- 앱 IntentParser가 보내는 `slots`를 그대로 쓴다
- 목표에 필요한 슬롯이 비어 있으면 지도 안내를 하지 않고 Claude가 안내한다

## 5. 안내

### 5.1 명령 시작 때 한 번 (#17 classify)

```
#17 POST /v1/elder/classify
요청 { commandId, utterance, ruleLevel, ruleApp, signals[], slots? }
응답 { commandId, intent, app, sensitivity: { level, category, reason, signals },
       route?: {                                                                              ← 추가
         role: "music", ask: false, named: false, mapVersion: "map@v12",
         candidates: [ … 4.3 모양 … ],
         confidence: { app: 0.44, role: 0.81 } },
       clarify?: { kind: "intent", questionId, say, options } }                               ← 하려는 일 묻기 (4.2 4번)
```

**안전 분류는 라우팅과 따로 늘 돈다** (14장 1).

- classify는 **안전 분류(규칙 + Claude)와 jev를 동시에** 돌린다. 안전 분류는 지금 서버 기획 5.2 그대로다 (사기 의심 신호는 L3, signals 보정, `max(ruleLevel, llmLevel)`)
- `sensitivity.level = max(안전 분류, 후보들의 검증된 목표 level)`. **목표 level은 올리는 데만 쓴다**
  - `candidate` 목표, 목표 없음, route 없음은 민감도를 바꾸지 않는다 (낮추는 근거로 쓰지 않음)
  - 폰이 후보를 고른 뒤 그 후보 목표의 민감도가 더 높으면 서버가 명령 민감도를 올리고 앱에 알린다 (5.2 응답)
- 사기 의심으로 L3이 나오면 route가 있어도 **지도 안내를 하지 않는다** (Claude + 멈춤 규칙)
- `clarify.kind: "goal"`은 응답 위쪽에 두지 않는다. 목표 질문은 **후보마다** 있다 (4.3)
- `commandId`는 앱이 명령 하나마다 만드는 값. 서버는 처음 받은 classify 요청의 **인증된 uid로 명령을 묶는다** (`CMD#<commandId>`의 `uid`). 다른 uid가 같은 `commandId`로 부르면 404 (14장 9)

### 5.2 앱 선택과 질문 답 (새 API)

```
POST /v1/elder/commands/{commandId}/app
요청 { appId, installState: "installed" | "unknown", askedUser: boolean, answer?: { questionId, option } }
응답 { goal?: { id, version, level }, sensitivity?: { level }, clarify?: … }   // 답으로 목표가 정해지면 그 목표
```

- 서버는 `appId`가 그 명령의 후보 안에 있는지 확인하고 **`chosenApp`으로 고정**한다. 한 번 고정하면 바꾸지 않는다 (바꾸려면 새 명령)
- 하려는 일 질문(`clarify.kind: "intent"`)의 답도 이 API로 받는다 → 서버가 그 역할로 후보를 다시 매겨 돌려준다
- guide 요청에 `appId`가 없거나, 고정된 앱이 없으면 **지도 안내를 하지 않는다** (v0.2의 "없으면 첫 번째 후보"는 폰이 실제로 고른 앱을 무시하므로 뺌: 14장 9)

### 5.3 화면마다 (#16 guide)

```
#16 POST /v1/elder/guide
요청 { …지금 필드…, commandId?, lastAction? }       ← 추가 (lastAction: 바로 앞 화면에서 실제 한 행동 { stepId, seq, action, text, dir? }, 3.6)
응답 { …지금 필드…, stepId?, source?: "map" | "ai" }   ← 추가 (stepId: 이 안내의 id. 어르신이 따르면 다음 요청의 lastAction.stepId로 돌아옴)
```

서버는 `CMD#`의 명령 상태(`chosenApp`, `progress`)를 보고:

1. 명령 없음·uid 다름, 고정된 앱 없음, 목표가 `verified` 아님, 사기 의심 L3, 기능 스위치 꺼짐 → **Claude**
2. 지금 화면의 앱 패키지가 고정된 앱이 아님 → Claude (앱 밖으로 나감)
3. **진행 상태 확인**: 직전 지도 안내의 `stepId`가 `lastAction.stepId`로 돌아왔고 행동이 맞으면 한 단계 진행. 안 돌아왔으면(어르신이 아직 안 함, 같은 화면 재요청) **같은 안내를 다시 준다** — 다음 단계로 넘어가거나 같은 행동을 두 번 시키지 않음 (14장 4)
4. 지도용 페이지 맞추기 조건(3.7)이 하나라도 안 맞음 → Claude
5. 지금 페이지가 목표의 도착지면 → `finish`의 다음 단계. 그 단계가 `verify: none`이거나 `sensitive`면 → **지도는 여기서 멈추고** Claude (민감하면 `stopped` 규칙)
6. 아니면 도착지까지 **`verified` 이동 연결선만으로 가장 짧은 길**을 찾는다 (메모리 스냅샷). 없으면 → Claude
7. 첫 연결선에 3.3 민감 검사를 **지금 화면에 다시** 한다. 걸리면 → Claude
8. 통과하면 **지도 안내**: 행동과 틀로 만든 문장으로 응답 (노드 번호는 지금 화면 것), `stepId`를 붙여 `progress`에 기록

- 지도 안내 중 한 번이라도 Claude로 넘어가면 그 명령은 그 뒤로 Claude가 안내한다
- 연결선을 따라 행동했는데(`lastAction`) 다음 화면이 `to`가 아니면 그 연결선의 실패로 센다 (8.3)

**한 단계씩 준다 (결정)**. 길 전체를 한 번에 폰에 보내지 않는다. 판단(페이지 맞추기·벗어남·민감 검사·학습 기록)이 서버 한 곳에 모인다.

|                                           | **한 단계씩 (이 문서)**                                                                 | 길 전체를 한 번에                                                |
| ----------------------------------------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 화면당 시간                               | 네트워크 왕복 + 스냅샷 조회 (Claude 없음). 0.1~0.3초 정도로 예상 (아직 재지 않음, 10장) | 거의 0초                                                         |
| 앱이 할 일                                | `lastAction`만 보냄                                                                     | 페이지 맞추기·민감 검사를 폰에도 만들어야 함 (두 곳 규칙 맞추기) |
| 길에서 벗어날 때, 다른 화면에서 시작할 때 | 서버가 바로 알고 다시 찾거나 Claude로 넘김                                              | 폰이 알아채고 서버를 불러야 함                                   |
| 멈춤 규칙                                 | 서버가 지킴                                                                             | 폰도 지켜야 함                                                   |

- **미리 보기는 하지 않는다** (14장 8). v0.2의 "다음 화면에서 `targetText`가 보이면 서버를 기다리지 않고 표시"는 다른 화면의 "확인"·"허용"도 표시할 수 있어 뺐다. 느리면 서버 쪽(스냅샷 메모리, Lambda 데우기)을 먼저 줄인다. 응답에 다음 단계를 **미리 받아 두는 것**(표시하지 않음)까지만 검토한다

## 6. 기록

Opus가 검토하려면 명령 하나의 안내 전체와 **마지막 화면**이 필요하다.

| 필요              | 지금 main                        | 바꿀 것                                                                                                                                                          |
| ----------------- | -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 명령 단위로 묶기  | guide 요청에 `requestId`만 있음  | 앱이 `commandId`·`lastAction`을 보냄 (5.3)                                                                                                                       |
| 끝났다는 신호     | 없음                             | `POST /v1/elder/commands/{commandId}/end` `{ result, finalScreen }`. `result`: `done` / `gave_up` / `stopped_user` / `stopped_safe`(멈춤 단계에서 정상으로 멈춤) |
| 마지막 화면       | 없음                             | 끝 신호에 **마지막 화면**(가림 적용)을 같이 보냄. 없으면 성공으로 쓰지 않음 (14장 13)                                                                            |
| 기록 남기기       | **dev에만** 디버그 저장소에 남김 | prod는 **개인정보 정책(12장 3)이 정해질 때까지 남기지 않음**. 정해지면 아래 가림을 적용해 남김                                                                   |
| 끝 신호가 안 오면 | –                                | 마지막 요청 뒤 30분이 지나면 `unknown`으로 닫음. `unknown`은 성공으로 쓰지 않음                                                                                  |
| 어르신 선호       | 없음                             | `done`이면 그 명령 앱의 역할 선호(`PREF#ROLE#<roleId>`)를 갱신                                                                                                   |

**prod 기록의 가림** (14장 7): 지금 `sensitive.ts`는 숫자(주민·카드·계좌·전화·금액)만 가린다. 이름·주소·질병·대화는 그대로다. prod 기록 전에 더할 것:

- 어르신이 말한 슬롯 값(이름·검색어)과 연락처에 있는 이름은 화면·말 어디서든 `[이름]`·`[검색어]`로 바꿈
- 입력 칸의 값은 남기지 않음 (칸이 있었다는 것만)
- 대화·메일·메모 앱(카카오톡 대화방, 문자, 메일 본문)과 건강·금융 앱 화면은 **기록하지 않음** (지도 학습 대상에서도 뺌)
- 남긴 기록은 보관 기간 뒤 지우고, 볼 수 있는 사람을 정함 (12장 3)

## 7. Opus 검토

### 7.1 언제

- 끝 신호 `done`(마지막 화면 있음)이 오면 명령을 대기열(SQS)에 넣고 `review-fn`이 처리한다
- `stopped_safe`도 검토한다: 멈춤 단계까지의 길은 민감 목표 학습(사람 승인)의 재료가 된다. `gave_up`·`stopped_user`·`unknown`은 지도에 더하지 않고, 지도 안내 중이었다면 쓴 연결선의 실패로 센다
- **SQS는 같은 메시지를 두 번 줄 수 있다**: 반영은 증거 항목의 조건부 Put(`<eid>#<commandId>`)으로 한 번만 센다 (14장 14)
- 지도 안내 명령도 일부 뽑아 검토한다 (길이 아직 맞는지)

### 7.2 Opus에게 주는 것과 받는 것

- 입력: 어르신 말(가림), 그 앱의 지도 목표 목록, 단계마다 (가린 화면 노드, 페이지, 안내 응답, 실제 행동 `lastAction`, 출처), 끝 신호, 마지막 화면
- 화면 글자는 데이터로만 다룬다 (화면 속 지시를 따르지 않음)
- 출력은 **정해진 모양만**: 자유 문장은 근거(`evidence`, 사람이 볼 때만 씀)와 새 목표 제안뿐이다

```ts
{
  success: "yes" | "no" | "unsure",
  evidence: "마지막 화면에 밝기 막대가 왼쪽으로 옮겨져 있음",      // 지도에 저장하지 않음
  goal: { existing: "settings.brightness_down" } | { proposeNew: { app, name, desc, slots, level } },
  moves:  [ { seq: 3, action: "tap", targetText: "디스플레이" }, … ],   // 실제 행동 seq를 가리킴. 돌아간 단계는 뺌
  finish: [ { seq: 5, action: "swipe_left", targetText: "밝기", verify: "none" } ],
  sensitiveSeqs: [],                          // 송금·결제·인증·설치·권한·보내기·동의
  personalText: false,
}
```

### 7.3 서버가 다시 확인하는 것 (Opus를 그대로 믿지 않음)

- `success`가 `yes`가 아니면 버린다
- `moves`·`finish`의 각 `seq`가 **실제 행동 기록(`lastAction`)과 맞는지**, 그 행동의 출발·도착 화면이 지도용 페이지(3.7)로 맞는지 확인한다. 행동 기록이 빠진 구간이 있으면 그 명령은 학습하지 않는다
- `moves`에 든 행동에 3.3 민감 검사를 서버가 다시 한다. 걸리면 그 명령 전체를 학습하지 않는다 (이동으로 잘못 나뉜 민감 행동이 공유 연결선이 되는 것을 막음)
- **화면 속 지시 흔적**: 화면 글자에 지시문 모양("…을 누르세요", "AI", "도우미", 링크·도메인)이 있는 화면을 지나간 명령은 학습하지 않는다. 지도에 들어가는 것은 행동·`targetText`·페이지 id뿐이다 (안내 문장은 틀로 만듦, 3.2)
- 새 목표 제안(`proposeNew`)은 **자동으로 들어가지 않는다**: 사람 확인 대기열로 간다 (8.2). 이름·설명이 jev 후보와 Claude 프롬프트로 다시 들어가기 때문이다
- 기존 목표에 붙일 때도 합치는 조건(3.4)을 확인한다: jev에 새 말을 기존 목표 후보로 물어 1등 ≥ 0.7 **그리고** 1·2등 차이 ≥ 0.3이고, 슬롯·민감도·도착지·끝 단계가 맞을 때만. 아니면 사람 확인
- 앱 자체에 대한 목표(깔기·업데이트·지우기)는 Play 스토어 목표로 옮긴다 (3.4)
- 민감도는 `max(규칙 판정, Opus 제안)`. Opus가 내릴 수 없다
- `personalText`가 `true`이거나 슬롯 자리 밖에 숫자·이름처럼 보이는 글자가 있으면 버린다

## 8. 지도에 반영하는 규칙

### 8.1 후보 → 검증됨

- 새 연결선·새 끝 단계는 `candidate`로 들어간다. candidate로는 **안내하지 않는다**
- **연결선**: 같은 키(출발 페이지·행동·방향·글자·도착 페이지)가 **서로 다른 어르신 2명 이상, 서로 다른 날 2일 이상**에서 성공하고, 앱 버전이 같으면 `verified`. 같은 날 같은 화면을 본 두 사람은 독립된 증거로 보기 어렵다 (14장 6)
- **목표의 끝 단계**: 같은 기준
- **dev**: 서로 다른 기기 2대, 날짜 조건 없음. prod는 위 기준
- 연결선은 여러 목표가 같이 쓰므로 목표마다 처음부터 모을 때보다 검증이 빨리 쌓인다

### 8.2 자동으로 넣지 않는 것

| 경우                                                                         | 처리                                      |
| ---------------------------------------------------------------------------- | ----------------------------------------- |
| **새 목표** (이름·설명이 새로 생김)                                          | **사람 확인** 대기 (디버그 뷰어에서 승인) |
| 목표 민감도 L2 이상, 또는 끝 단계에 송금·결제·본인인증·설치·권한·보내기·동의 | **사람 승인** 대기                        |
| 금융 앱(은행·증권·카드), 사기 의심 신호가 있던 명령                          | 지도에 넣지 않음                          |
| 대화·메일·메모·건강 앱                                                       | 지도에 넣지 않음 (6장 기록 제외와 같음)   |
| 앱 밖 웹 주소로 이어지는 길, 설치 앱이 아닌 패키지                           | 지도에 넣지 않음                          |

- 자동으로 자라는 것은 **이미 있는 목표의 이동 연결선과 끝 단계**다. 새 목표는 사람이 확인하는 만큼만 늘어난다
- 승인된 민감 목표도 지도 안내는 **멈춤 단계에서 `stopped`로 끝난다**

### 8.3 낡은 길 내리기

- 연결선을 따라 행동했는데 도착 페이지가 다르거나, 지도 안내 중 Claude로 넘어가거나, `gave_up`·`stopped_user`로 끝나면 쓴 연결선·끝 단계의 실패로 센다
- 최근 20번 중 실패가 30%를 넘으면 `candidate`로 내리고 `demotedAt`을 적는다. **다시 올리려면 내려간 뒤의 새 성공**이 8.1 기준만큼 필요하다 (예전 성공으로 바로 다시 올라가지 않음, 14장 14)
- 앱 버전이 바뀌면 그 버전에는 연결선이 없어서 자연스럽게 Claude로 넘어간다. 새 버전에서 성공한 연결선이 새로 쌓인다
- 90일 동안 안 쓰인 연결선은 `retired`
- 문제가 보이면 사람이 긴급 차단 목록(3.5)에 넣어 바로 막는다

## 12. 정할 것

1. **민감한 목표(L2 이상)**: 사람 승인으로 넣을지(이 문서의 제안), 지도에서 아예 뺄지
2. **검증 기준**: prod 어르신 2명·2일(제안), dev 기기 2대
3. **prod 기록과 개인정보 (지도 학습의 전제)**: 남길 범위(6장 가림·제외 목록), 보관 기간(제안 30일), 볼 수 있는 사람, 삭제 요청 처리, 어르신·보호자 동의 문구. **정해지기 전에는 prod 학습을 켜지 않는다**
4. **외부 전송**: 어르신 말이 OpenRouter·TypeSafe로 나가는 것을 허용할지, ZDR이 이 엔드포인트에서 되는지 (안 되면 prod에서 jev를 쓰지 않음)
5. **고령자 앱 변경 요청**: `commandId`, `lastAction`(`stepId`·`seq` 포함), 앱 선택 API, 끝 신호(마지막 화면), 후보 고르기·설치 확인 세 상태·설치 묻기·민감 역할 묻기, 설치 확인 방법 A/B/C(Play 정책, 접근성 서비스에서 되는지), 후보마다 `clarify`. 앱 IntentParser goal 코드와 지도 목표 id를 어떻게 맞출지
6. **새 목표 확인**: 누가 확인하나 (팀, 뷰어 화면), 얼마나 자주
7. **역할 기본 앱**: 처음 기본값을 누가 정하고, 보호자 앱에서 바꿀 수 있게 할지
8. **OpenRouter 계정·결제**: 개인 키로 시험함. 팀 계정과 사용 한도
9. **보호자 권한을 목표 단위로**: 보호자 앱이 "정부24 등본은 알림만, 은행 송금은 승인" 같은 설정을 할지
10. **서버 기획 9장(캐싱)**: 이 문서의 지도 안내가 9장 캐싱을 대신하는지, 따로 두는지

v0.2:

- 카탈로그 → **데이터로 된 지도** (역할·앱·목표·연결선), 목표마다 id·버전

- 캐시 대신 **지도 안내 모드**: 지금 페이지에서 목표 도착지까지 검증된 연결선으로 길 찾기
- **목표 = 도착지 + 끝 단계, 이동은 모든 목표가 같이 쓰는 연결선**
- 고르기는 **앱 → 목표 2단계로 확정**, 큰 목록 시험(2.2)
- **역할**로 같은 일을 하는 앱을 묶고, 역할 합계로 판정. 앱 자체에 대한 일은 Play 스토어 목표
- **서버는 후보 앱 순서만 보내고 폰이 깔린 첫 번째를 고름** (2.3 시험: 99.6%)
- route는 서버가 `commandId`로 저장. 기록·끝 신호·선호 저장. 지도는 실제 사용으로만 자람 (3.6)

v0.3:

- **안전 분류는 늘 따로 돎**. jev·목표 민감도는 올리는 데만 (5.1)
- **연결선은 부작용 없는 이동만**. 민감 단어·권한 창·같은 페이지 안 행동은 끝 단계로. 안내 직전에 다시 검사 (3.3)
- **지도용 엄격 페이지 맞추기(match@v2)**: 상태·위치·앱 버전·누를 글자가 하나뿐인지 (3.7)
- **끝 단계는 확인할 수 있어야 자동 진행**, 명령 진행 상태·`stepId`로 같은 행동을 두 번 시키지 않음 (3.2, 5.3)
- `lastTap` → **`lastAction { stepId, seq, action, text, dir }`**, 빠진 구간은 학습하지 않음 (3.6)
- **안내 문장은 저장하지 않고 틀로 만듦**, 새 목표는 사람 확인, 화면 속 지시 흔적이 있는 명령은 학습하지 않음, 검증은 어르신 2명·2일 (7.3, 8)
- **prod 기록은 개인정보 정책 뒤에**, 가림 범위 넓힘·기록 제외 앱, ZDR 강제, jev에 보내는 것 고쳐 적음 (6, 9)
- **미리 보기 뺌** (5.3)
- **앱 선택 API로 고른 앱 고정**, 없으면 지도 안내 안 함. `commandId`를 uid에 묶음 (5.1, 5.2)
- 1단계 판정 순서: **'해당 없음'·애매함 먼저, "말한 앱"은 별칭으로** (4.2). 후보마다 `clarify`, 목표가 약해지는 후보는 뒤로, 설치 동의는 새 명령 (4.3)
- 합치기는 점수 + 차이 + 슬롯·민감도·도착지·끝 단계가 맞을 때만 (3.4, 7.3)
- 설치 확인 세 상태(`installed`/`missing`/`unknown`) (4.4)
- 연결선 키에 행동·방향, 앱 버전별, 증거는 명령마다 한 번(SQS 중복), 내려간 뒤엔 새 증거로만 다시 올림 (3.3, 7.1, 8.3)
- 저장은 DynamoDB 원본 + **S3 스냅샷 게시**, 명령마다 지도 버전 고정, 긴급 차단 (3.5)
- 끝 신호에 **마지막 화면**, `stopped_safe` 따로, 측정에 실제 끝 화면 확인 (6, 7.1, 10)
