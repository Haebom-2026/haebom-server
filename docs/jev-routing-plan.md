- 작성일: 2026-11-26 (v0.1), 2026-11-27 (v0.2)
- 상태: **기획**. 구현 전
- 관련: [서버 기획](server-plan.md) 5.2 classify·5.3 guide·9장 캐싱·12.7.1 화면 매칭, [S5 guide API](api/s5-guide.md)
- v0.2에서 바뀐 것: 13장

## 0. 한 줄 요약

어르신의 말을 **jev(고르기 전용 모델)로 지도에 있는 "어느 앱의 어느 목표"인지 두 단계로 고르고**, 지금 화면에서 그 목표의 도착지까지 **검증된 연결선**이 있으면 Claude 없이 지도대로 안내한다. 길이 없거나 화면이 어긋나면 지금처럼 Claude가 안내한다. 명령이 끝나면 **Opus가 기록을 검토해 성공한 길만 지도에 더한다**. 지도는 사용하면서 저절로 자라지만, 아무 길이나 들어가지 않는다.

```
어르신 말 ─▶ jev 1단계: 앱 (지도의 앱 전체, 같은 역할 앱은 묶어서) → 후보 앱 순서 (최대 3개)
            jev 2단계: 후보 앱들의 목표 (동시에)
            폰: 후보 중 깔린 첫 번째 앱 (설치 앱 목록은 폰 밖으로 안 나감)
   ├─ 목표 + 도착지까지 검증된 연결선 ─▶ 【지도 안내】 화면마다 페이지 맞추기 → 다음 연결선 → 도착하면 목표의 끝 단계
   │        └─ 화면이 지도와 다름 ─▶ 그 자리부터 Claude
   ├─ 목표는 있는데 길 없음 ─▶ 【Claude 안내】 (route를 알려 줌)
   └─ 실패 (해당 없음·애매함·오류) ─▶ 【Claude 안내】 지금 흐름 그대로
                    │
          명령이 끝나면 (앱의 끝 신호)
                    ▼
     【Opus 검토】 비동기, 어르신을 기다리게 하지 않음
       ① 정말 성공했나 (마지막 화면 근거)
       ② 돌아간 길을 빼고, 이동(연결선)과 이 목표만의 끝 단계로 나눔
       ③ 개인 값 → 슬롯 ("임영웅" → {검색어})
       ④ 기존 목표인가, 새 목표인가 (중복 검사)
                    ▼
     지도에 반영 (8장 규칙): 후보 → 서로 다른 어르신 성공이 쌓이면 검증됨
```

## 1. 왜 하나

| 문제                                                                                                   | 이 구조가 푸는 방법                                                                   |
| ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| Sonnet guide는 요청마다 약 $0.0055(캐시 없으면 약 $0.02), 1.8~4.1초                                    | 검증된 길이 있는 목표는 화면마다 Claude를 부르지 않음                                 |
| 어르신 말이 제각각이라 캐시 키로 못 씀 ("등본 떼 줘" / "주민등록 등본 발급 받고 싶어" / "정부24 등본") | jev가 모두 `gov24.resident_copy` 하나로 모음 → 길을 목표 단위로 모을 수 있음          |
| 앱·목표를 사람이 미리 다 적을 수 없음                                                                  | 실제 사용에서 Claude가 성공한 안내를 Opus가 검토해 **지도에 더함**                    |
| 목표는 다른데 길은 거의 같음 (화면 밝게 / 어둡게)                                                      | 이동은 **모든 목표가 같이 쓰는 연결선**, 목표에는 도착지와 끝 단계만 둠               |
| 민감도(S4)를 말마다 LLM으로 판단하면 느리고 흔들림                                                     | 목표마다 민감도를 적어 둠. 보호자 권한도 목표 단위로 걸 수 있음                       |
| 글을 만드는 모델은 엉뚱한 값을 낼 수 있음                                                              | jev는 **목록 안에서 고르기만** 하고 후보별 확률을 줌 → 애매하면 확실하게 넘길 수 있음 |

## 2. jev 시험 결과

OpenRouter Decisions API(`POST /api/alpha/decisions`, 모델 `typesafe/jev-1.14`, `choice` 질문).

### 2.1 작은 목록 (2026-11-26)

말 64개(실제 폰 요청 24 + 직접 쓴 40, 해당 없음 7개 포함), 앱 11개·목표 5개 앱.

| 시험                        | 그대로 쓸 때             | 기준을 두면                                       |
| --------------------------- | ------------------------ | ------------------------------------------------- |
| A. 말 → 앱                  | 98% (63/64)              | 1등 ≥ 0.5: 97% 받아들임, 그중 **100%** 정확       |
| B. 말 + 앱 → 목표           | 98% (42/43)              | 1등 ≥ 0.7·차이 ≥ 0.3: 93% 받아들임, 그중 **100%** |
| C. 화면 + 할 일 → 누를 노드 | 42% (Claude와 같은 버튼) | 1등 ≥ 0.9: 18%만 받아들임 → **쓰지 않음**         |

- 속도: 중앙값 0.53초, 최대 0.76초. 비용: 호출당 약 $0.00004 (입력 100만 토큰당 $0.042, 출력 $0)
- 겹치기 쉬운 쌍(등본/초본, 연락처 저장/전화 걸기/카톡 친구 추가, 사진 보기/찍기, 유튜브 검색/그냥 틀기)과 목록에 없는 말 7개는 모두 맞힘

→ **앱·목표 고르기(A·B)에만 쓴다.** 화면에서 누를 버튼은 지도의 `targetText` 또는 Claude가 정한다.

### 2.2 큰 목록 (2026-11-27)

앱이 늘어도 버티는지. 말 98개(2.1의 64 + 새로 쓴 34), 앱 후보 11 / 30 / 60개, 목표는 지금 목록과 큰 목록(앱당 7~24개, 밝게/어둡게·글자 크게/작게·소리 크게/작게 같은 비슷한 쌍 포함). 약 800번 호출, $0.037.

| 구분                      | 그대로 쓸 때 | 받아들임 | 그중 정확 | 시간 중앙값 | 호출당 비용 |
| ------------------------- | ------------ | -------- | --------- | ----------- | ----------- |
| 앱 11개                   | 95%          | 70%\*    | 97.1%     | 0.52초      | $0.00003    |
| 앱 30개                   | 94%          | 93%      | 94.5%     | 0.52초      | $0.00006    |
| 앱 60개                   | 91%          | 89%      | 97.7%     | 0.52초      | $0.0001     |
| 목표, 지금 목록           | 98%          | 95%      | 100%      | 0.52초      | –           |
| **목표, 큰 목록 (≤24개)** | **100%**     | 95%      | **100%**  | 0.52초      | –           |

\* 11개 시험에서는 새 말 상당수의 정답이 '해당 없음'이라 받아들임이 낮다.

- **개수는 문제가 아니다**: 앱 60개에서도 시간이 같고, 24개 목표 안의 비슷한 쌍을 모두 맞힘 → 2단계(앱 하나의 목표만 물음)가 잘 버팀
- **틀린 것은 같은 역할 앱 사이**: "트로트 틀어 줘" → 멜론, "임영웅 콘서트 검색해 줘" → 네이버. 같은 역할 앱을 허용해 다시 채점하면 앱 30·60개 모두 **받아들인 것 중 100%** (4.3에서 역할로 묶음)
- 같은 역할 앱이 여럿이면 확률이 나뉘어(멜론 0.44 + 지니 0.20 …) 1등이 0.5 아래로 → 받아들임이 86~89%로 줄어듦 (안전하게 Claude로 넘어감) → 역할 합계로 판정 (4.2)
- **"배달의민족 깔아 줘" → 배달의민족 앱 0.90** (받아들였는데 틀림). 1단계 지시문에 "앱 이름이 있어도 깔기·업데이트·지우기면 Play 스토어"를 넣으니 Play 스토어 0.90으로 고쳐짐 (3.4)
- 한계: 새 말 34개와 정답은 직접 씀. 설치 앱으로 좁히는 효과는 반영하지 않음 (2.3에서 잼)

### 2.3 후보를 보내고 폰이 고르기 (2026-11-27)

4.3·4.4의 방식 시험. 서버는 지도 앱 60개 전체로 1단계를 고르고, 역할로 묶어 후보 앱을 최대 3개 순서대로 낸 뒤, 후보 중 목표가 있는 앱의 2단계를 동시에 부른다. 폰은 설치 앱이 무작위로 다른 가상 폰 30대(앱마다 30%, 유튜브·카톡 95%, 기본 앱 100%)가 후보 중 깔린 첫 번째 앱을 고른다. 말 98개, $0.023.

| 항목                                                   | 결과                             |
| ------------------------------------------------------ | -------------------------------- |
| 서버가 후보를 낸 89개 중 정답 앱이 후보 안에 있음      | **100%**                         |
| 폰이 깔린 첫 번째 후보를 고름                          | 95.7%                            |
| **+ 말한 앱이 분명하면(1등 ≥ 0.7) 그 앱만 후보 (4.3)** | **99.6%**                        |
| 2단계 목표 (정답 앱)                                   | 그대로 100%, 받아들인 것 중 100% |
| 명령 하나 고르는 시간 (1단계 + 2단계 동시)             | 중앙값 0.94초, 최대 1.15초       |
| 명령당 비용                                            | $0.00012                         |
| 2단계를 동시에 부른 앱 수                              | 평균 0.5개, 최대 1개             |

- 95.7%에서 틀린 것은 거의 모두 **말한 앱이 폰에 없어서 같은 역할 앱으로 바꾼 것**: 카톡 보내 줘 → 문자, 멜론에서 → 유튜브, 넷플릭스 → 유튜브, 쿠팡에서 → 11번가, KTX → SRT → 4.3에 "말한 앱이 분명하면 바꾸지 않고 설치를 물음" 규칙을 둠
- 남은 틀림 2개는 역할 설계 문제: 크롬을 '검색' 역할에 넣음(→ 크롬은 따로), 네이버 지도(0.69)가 '지도'·'대중교통' 두 역할이라 합계가 큰 대중교통 쪽 지하철 앱으로 바뀜(→ 여러 역할 앱의 역할 고르기는 4.2 주의 참고)
- Claude로 넘어간 것(7개: "은행에 돈 보내야 돼", "설치해 줘" …)과 하려는 일을 물은 것(2개: "임영웅 찾아줘" 음악 0.29 / 영상 0.26)은 모두 안전한 쪽
- 한계: 가상 폰의 설치 확률·말 34개·역할 묶음은 직접 정함. 실제 폰에서 패키지 확인이 되는지는 앱 팀 확인 필요 (4.4)

## 3. 지도

지도는 코드가 아니라 **데이터**다. 사용하면서 늘어나므로 배포 없이 바뀌어야 한다. 처음 목록(앱 10개 × 목표 2~6개)은 손으로 넣고(`origin: seed`), 그 뒤는 Opus 검토로 늘어난다(`origin: learned`).

지도는 네 가지로 이루어진다.

```
역할 (음악, 검색, 은행 …)
 └ 앱 (유튜브, 멜론 …)            ← jev 1단계 후보
    └ 목표 (도착지 + 끝 단계)      ← jev 2단계 후보
페이지 ──연결선──▶ 페이지          ← 모든 목표가 같이 쓰는 이동
```

### 3.1 역할과 앱

```ts
// 역할 (제안)
{ id: "music", name: "노래 듣기", defaultApp: "youtube", sensitive: false }
{ id: "bank",  name: "은행",      defaultApp: null,      sensitive: true  }

// 앱 (제안)
{ id: "melon",   name: "멜론",   desc: "노래 듣기, 음원 검색",       roles: ["music"],          packages: ["com.iloen.melon"] }
{ id: "youtube", name: "유튜브", desc: "영상·노래·공연 찾아보기",    roles: ["video", "music"], packages: ["com.google.android.youtube"] }
```

- `roles`: 같은 일을 하는 앱끼리 묶는다 (4.3). 한 앱이 여러 역할일 수 있다 (유튜브 = 영상·음악). 역할이 하나뿐인 앱도 있다 (정부24 → 공공 서류)
- 역할은 **같은 일을 대신할 수 있는 앱**끼리만 묶는다. 웹 브라우저(크롬)처럼 무엇이든 되는 앱은 '검색' 같은 역할에 넣지 않고 따로 둔다 (2.3)
- `defaultApp`: 습관으로 못 정할 때 앞에 세우는 앱. 보호자가 바꿀 수 있게 한다. 민감한 역할은 두지 않는다
- `packages`: 폰이 깔려 있는지 확인할 때 쓴다 (4.4)

### 3.2 목표 = 도착지 + 끝 단계

```ts
// 목표 하나 (제안)
{
  id: "settings.brightness_down",     // 한 번 쓴 id는 지운 뒤에도 다시 쓰지 않음
  version: 2,                         // 설명·민감도·슬롯·끝 단계가 바뀌면 올림
  app: "settings",
  name: "화면 어둡게",                 // 어르신께 물을 때 보여 주는 짧은 이름
  desc: "화면을 더 어둡게 (눈부심 줄이기)",   // jev 후보 설명
  level: "L0", category: "settings",  // S4 민감도
  approvalAction: null,               // S3 승인 action (있으면)
  slots: [],                          // 필요한 값. 예: youtube.search → ["query"]
  arrive: ["pg_brightness"],          // 도착 페이지 (match@v1 pageId, 앱 버전마다 다를 수 있어 여러 개)
  finish: [                           // 도착한 뒤 이 목표만 하는 단계 (1~3개)
    { page: "pg_brightness", action: "swipe_left", targetText: "밝기", say: "막대를 왼쪽으로 밀어 주세요" },
  ],
  stopAt: null,                       // 멈춤 단계 번호 (송금·결제·설치·권한·보내기 확인이면)
  status: "verified",                 // candidate | verified | retired
  origin: "learned",                  // seed | learned
}
```

- 밝게 / 어둡게는 `arrive`가 같고 `finish`만 다르다. 이동은 3.3의 연결선을 같이 쓴다
- 개인 값은 슬롯 자리(`{query}`, `{name}`)로 저장한다. 예: `youtube.search`의 `finish`는 `[검색창에 type {query}, 결과 확인]`
- 모든 질문에 **`none`(해당 없음)** 후보를 넣는다. 고르기 모델은 맞는 답이 없어도 무언가를 고르기 때문
- 목표가 없는 앱(갤러리, 카메라 등)은 `<앱>.open` 하나로 본다 (`arrive` = 앱 첫 화면, `finish` 없음)
- jev 후보에는 `candidate`·`verified` 목표를 모두 넣는다. 고르는 것과 지도로 안내하는 것은 따로다

### 3.3 연결선 (모든 목표가 같이 씀)

```ts
{
  id: "e_91c2",
  from: "pg_settings_home",           // match@v1 pageId
  to: "pg_display",
  action: "tap", targetText: "디스플레이",   // swipe면 dir, 앱 밖 이동이면 home·back
  say: "'디스플레이'를 눌러 주세요",
  pkgVersion: "15.0",
  stats: { successes: 9, elders: 4, mapGuided: 30, mapFailures: 1 },
  status: "verified",                 // candidate | verified | retired
}
```

- **노드 번호는 저장하지 않는다**. `targetText`로 지금 화면에서 다시 찾는다
- 연결선은 **이동만** 담는다 (누르기·밀기·뒤로). 글자 넣기처럼 목표마다 다른 행동은 목표의 `finish`에 둔다
- 어느 목표를 하다가 성공했든 연결선의 성공으로 센다. 밝기를 올리다 성공한 어르신 덕에 "설정 → 디스플레이"가 검증되면, 글자 크기 목표도 그 연결선을 바로 쓴다
- "다음", "확인"처럼 흔한 글자는 화면마다 다른 곳으로 갈 수 있다 → 연결선은 출발 페이지가 `exact`·`similar`로 맞을 때만 쓰고, 도착 페이지가 `to`와 다르면 실패로 센다

### 3.4 중복을 없애는 규칙

| 겹침                                     | 예                                    | 처리                                                                             |
| ---------------------------------------- | ------------------------------------- | -------------------------------------------------------------------------------- |
| 같은 뜻, 이름만 다름                     | 등본 발급 / 등본 떼기 / 등본 출력     | **하나로 합침**. 다른 이름은 `desc`에 넣음                                       |
| 결과가 같음                              | 등본 PDF 받기 / 등본 출력             | **하나로 합침** (갈림은 화면에서 어르신이 고름)                                  |
| **결과는 다른데 길은 같음**              | 화면 밝게 / 어둡게, 글자 크게 / 작게  | **목표는 나누고 길은 같이 씀** (도착지 같음, `finish`만 다름)                    |
| 비슷하지만 정말 다름                     | 등본 / 초본, 송금 / 잔액 조회         | 남기고 `desc`에 **차이를 만드는 말**을 적음. 그래도 애매하면 어르신께 물음 (4.2) |
| 같은 일을 하는 다른 앱                   | 유튜브 / 멜론 / 지니                  | 앱은 따로, **역할로 묶음** (4.3)                                                 |
| 앱 자체에 대한 일 (깔기·업데이트·지우기) | "배달의민족 깔아 줘", "카톡 업데이트" | 그 앱이 아니라 **Play 스토어 목표** (`playstore.install` + 슬롯 `{appName}`)     |

새 목표가 들어올 때 서버가 이 규칙을 기계로 확인한다 (7.3).

### 3.5 저장

원본은 DynamoDB main 테이블 (제안 키):

| 엔티티      | PK            | SK                   | 주요 속성                                                 |
| ----------- | ------------- | -------------------- | --------------------------------------------------------- |
| 역할        | `MAP`         | `ROLE#<roleId>`      | name, defaultApp, sensitive                               |
| 앱          | `MAP`         | `APP#<appId>`        | name, desc, role, packages                                |
| 목표        | `MAP`         | `GOAL#<goalId>`      | version, name, desc, level, slots, arrive, finish, stopAt |
| 연결선      | `PAGE#<from>` | `EDGE#<edgeId>`      | to, action, targetText, say, stats, status, pkgVersion    |
| 지도 버전   | `MAP`         | `VERSION`            | n (바뀔 때마다 +1)                                        |
| 어르신 선호 | `ELDER#<eid>` | `PREF#ROLE#<roleId>` | appId, updatedAt (4.3)                                    |

- ai-fn은 지도를 읽어 **몇 분 동안 메모리에 둔다** (`VERSION`이 바뀌면 다시 읽음). 연결선은 페이지 기준으로 모아 둬서 길 찾기(5.2)를 메모리에서 한다
- 변경은 모두 기록한다 (누가: seed / opus / 사람, 언제, 무엇을). 목표·연결선 단위로 되돌릴 수 있게

### 3.6 지도 만들기

**지도는 실제 사용으로만 자란다**: Claude 안내 → 끝 신호 → Opus 검토 → 후보 → 검증됨 (6~8장). 처음엔 지도가 비어 있어도 손해가 없다. 길이 없으면 Claude가 안내하는데, 이것이 지금 동작 그대로다. 지도가 자라는 만큼 Claude 호출이 줄어든다. 실제 어르신 폰의 앱 버전·화면으로만 만들어진다는 점도 장점이다.

| 층     | 어떻게 생기나                                                                                                                                                               | 지금 상태                                                                                                        |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 페이지 | 화면이 들어올 때마다 `match@v1`이 이미 본 페이지인지 판정, `new`면 새 페이지                                                                                                | **이미 dev에서 저절로 생기고 있음** (디버그 뷰어 화면 지도). 서비스 저장소로 옮기기·정확도 측정(match@v2)이 남음 |
| 연결선 | 같은 `commandId`의 guide 요청을 순서대로 보면 `화면 N(페이지 A) + 안내(tap "디스플레이") + 화면 N+1(페이지 B)` → 후보 `A --"디스플레이"--> B`. Opus 검토로 돌아간 단계를 뺌 | `commandId`가 없어 아직 못 만듦                                                                                  |
| 목표   | 처음 목록(역할·앱·목표)은 손으로 넣고, 그 뒤는 Opus가 기존 목표에 붙이거나 새 후보를 만듦 (7.3)                                                                             | 시험용 목록(앱 10개, 큰 목록 60개)만 있음                                                                        |

- **실제로 누른 것**: 서버는 무엇을 누르라고 했는지만 알고, 어르신이 실제로 누른 것은 모른다 (다음 화면이 그럴듯하면 따랐다고 추정할 뿐). 앱은 접근성 이벤트로 실제 누른 노드를 알 수 있으므로 guide 요청에 선택 필드 `lastTap: { text }`(바로 앞 화면에서 누른 노드의 글자)를 받는다 (5.2). 있으면 연결선을 안내가 아니라 **실제 누른 것**으로 만든다
- **dev 기록을 시간으로 묶어 연결선을 뽑는 것은 하지 않는다**. `commandId`가 없는 지난 기록은 어느 명령인지 정확히 알 수 없어 틀린 연결선이 들어가기 쉽다
- **팀 녹화는 시연용으로만**: 시연을 꼭 지도 안내로 보여 줘야 하면, 팀이 실제 폰에서 흐름을 따라가며 `scripts/adb-capture`로 보내고 목표 이름을 붙여 같은 과정을 태운다. **사람 승인**으로 넣고(`origin: seed`), 실제 사용에서 실패가 쌓이면 똑같이 내려간다 (8.3)
- 지도가 자라는 것은 **앱이 `commandId`·끝 신호를 보내기 시작한 뒤**다 (R6). 서버 쪽(R1~R5)은 먼저 만들어 둔다

## 4. 고르기 (jev)

### 4.1 두 단계로 묻기

**결정: 앱을 먼저 고르고, 그다음 그 앱의 목표를 고른다 (2단계).** 앱과 목표는 지도가 자라면서 계속 늘어나므로, 한 번에 앱 질문과 모든 앱의 목표 질문을 넣는 방식(v0.1)은 쓰지 않는다. 목표 질문에는 언제나 **고른 앱 하나의 목표만** 들어가서, 앱이 늘어도 목표 후보 수는 앱 하나 분량으로 유지된다 (2.2: 24개 목표에서도 100%).

```
1단계  POST decisions { state: 말, questions: { app: 지도의 앱 전체 + none } }
         └─ 판정 (4.2) → 후보 앱 순서 (4.3). 실패면 Claude, 2단계 안 감
2단계  후보 앱 중 목표가 있는 앱마다 POST decisions { goal: 그 앱의 목표 후보 + none } — 동시에
         └─ 목표가 하나뿐인 앱(<앱>.open)은 건너뜀. 2.3에서 동시 호출은 평균 0.5개, 최대 1개
```

- 1단계 지시문에 **"말에 앱 이름이 들어 있어도 그 앱을 새로 깔기·업데이트·지우려는 말이면 Play 스토어"**를 넣는다 (2.2)
- 서버는 그 폰에 무엇이 깔렸는지 모른다. 1단계는 지도의 앱 전체로 고르고, 깔린 앱 고르기는 폰이 한다 (4.3·4.4)
- 시간: 호출당 약 0.5초 → 1단계 + 2단계(동시)로 약 1초 (2.3: 중앙값 0.94초, 최대 1.15초). classify는 명령 시작 때 한 번이라 화면마다 늘지 않는다. 두 호출을 합쳐 1.5초가 넘으면 실패로 보고 Claude로 넘긴다
- 비용: 앱 60개에서도 호출당 약 $0.0001 → 명령당 약 $0.00012 (2.3)
- 앱 후보가 아주 많아 1단계 정확도가 떨어지면, 역할을 먼저 고르는 단계를 하나 더 두는 것을 검토한다 (지금 60개까지는 필요 없음)

```json
// 1단계
{ "model": "typesafe/jev-1.14", "state": "어르신이 한 말: 등본 떼 줘",
  "questions": { "app": { "type": "choice", "instructions": "…", "criteria": { "gov24": "…", "youtube": "…", "none": "…" } } } }
// 2단계 (1단계에서 gov24)
{ "model": "typesafe/jev-1.14", "state": "어르신이 한 말: 등본 떼 줘",
  "questions": { "goal": { "type": "choice", "instructions": "정부24에서 하려는 일은?…", "criteria": { "resident_copy": "…", "resident_abstract": "…", "none": "…" } } } }
```

### 4.2 받아들이는 기준 (시작값, 10장에서 조정)

**1단계 (앱)** — 위에서부터 처음 맞는 줄:

| 결과                                                                           | 처리                                                                                                |
| ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| 1등 앱 ≥ 0.7, `none` 아님 (**말한 앱이 분명함**: "카톡 보내 줘", "멜론에서 …") | 후보 = **그 앱 하나**. 같은 역할 앱으로 바꾸지 않음 (4.3) → 2단계                                   |
| 1등 앱 ≥ 0.5                                                                   | 후보 = 그 앱 + 같은 역할 앱 (4.3) → 2단계                                                           |
| 앱들의 확률을 **역할별로 더해** 1등 역할 ≥ 0.5 (예: 멜론 0.44 + 지니 0.20)     | 역할 확정 → 후보 = 그 역할 앱 (4.3) → 2단계                                                         |
| 1·2등 역할이 둘 다 0.25 이상이고 차이 < 0.2 ("임영웅 찾아 줘": 영상 / 연락처)  | **하려는 일을 물음**: 역할 `name`으로 options ["영상 찾기", "연락처 찾기"]. 앱 이름을 늘어놓지 않음 |
| `none`, 그 밖                                                                  | **실패** → 지금 흐름 (Claude)                                                                       |
| jev 오류·두 호출 합쳐 1.5초 초과                                               | **실패** → 지금 흐름. jev 장애가 안내를 막지 않음                                                   |

- 주의: 1등 앱이 여러 역할이면(네이버 지도 = 지도·대중교통) 확률 합이 큰 역할을 고르면 말과 어긋날 수 있다 (2.3: "서울역 가는 길" → 지하철 앱). 1등 앱이 분명하면 그 앱이 먼저이고, 뒤에 붙이는 같은 역할 앱은 **1등 앱의 모든 역할**에서 확률 순으로 고른다. R1에서 다시 잰다

**2단계 (목표)** — 후보 앱마다:

| 결과                                                                 | 처리                                                                                                 |
| -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 목표 1등 ≥ 0.7 이고 1·2등 차이 ≥ 0.3, `none` 아님                    | **성공** → route = (앱, 목표)                                                                        |
| 목표 1·2등이 둘 다 0.3 이상이고 차이 < 0.3 (예: 등본 0.5 / 초본 0.4) | **어르신께 물음**: 목표 `name`으로 options ["등본", "초본"]. 답을 받으면 그 목표로 확정. Claude 없음 |
| 그 밖 (목표 `none`, 1등 < 0.7)                                       | route = (앱, 목표 없음). 앱만 확정, 안내는 Claude                                                    |

### 4.3 후보 앱 순서와 폰의 고르기

서버는 **순서를 매긴 후보 앱(최대 3개)**만 보내고, 폰이 **후보 중 깔린 첫 번째 앱**을 쓴다. 판단 규칙(순서 매기기)은 서버에 있으므로 규칙을 바꿔도 앱을 업데이트하지 않는다. 폰은 "깔린 첫 번째"만 한다.

**서버가 순서를 매기는 법**

| 경우                                    | 후보                                                                                                      |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 말한 앱이 분명함 (1등 앱 ≥ 0.7)         | **그 앱 하나**. 없으면 같은 역할 앱으로 바꾸지 않는다 (2.3: 카톡 → 문자, 멜론 → 유튜브로 바꾸면 틀림)     |
| 그 밖 (역할로 정해짐, "트로트 틀어 줘") | 그 역할 앱을 ① 이 어르신이 평소 쓰던 앱(`PREF#ROLE#music`) ② 역할 기본 앱(`defaultApp`) ③ jev 확률 순으로 |

**폰이 하는 일**

| 경우                                 | 처리                                                                                                                |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| 깔린 후보가 있음                     | 첫 번째를 쓰고, guide 요청에 `appId`로 알림 (5.2)                                                                   |
| 말한 앱(후보 하나)이 안 깔림         | "멜론이 없어요. 설치할까요?" → 예면 `playstore.install` (슬롯 `{appName}`), 아니면 끝                               |
| 역할 후보가 하나도 안 깔림           | "노래 들을 앱이 없어요" + 기본 앱 설치를 권함                                                                       |
| 민감한 역할 (`ask: true`, 은행·결제) | 순서대로 고르지 않는다. **깔린 후보만** 선택지로 보여 주고 묻는다 ("국민은행, 농협 중 어느 거요?"). 하나뿐이면 그것 |

- 어르신 선호는 끝 신호 `done`인 명령의 앱으로만 갱신한다 (6장). 묻고 받은 답도 선호로 저장해 다음엔 안 묻는다
- 서버는 어르신 폰에 무엇이 깔렸는지 모르지만, 실제로 쓴 앱은 guide 요청의 `appId`·화면 `pkg`로 안다 (지금도 화면 `pkg`는 받고 있음)

### 4.4 설치 확인은 폰 안에서

설치 앱 목록은 **폰 밖으로 보내지 않는다**. 서버가 보낸 후보 몇 개가 깔려 있는지만 폰이 확인한다. 설치 앱 목록은 개인정보(은행·건강·종교 앱 등)라서, 서버가 받지 않는 쪽이 깔끔하다.

다만 안드로이드 11부터는 **"이 앱 하나가 깔려 있나?"라고 묻는 것도** 볼 권한이 없으면 "없음"으로 나온다 (`getPackageInfo`, `getLaunchIntentForPackage` 모두). 볼 권한은 manifest `<queries>`에 미리 선언해야 하는데, manifest는 빌드할 때 고정이라 지도가 자라며 생기는 새 패키지를 적어 둘 수 없다.

| 방법                             | 내용                                                                                                                             | 장단점                                                                                                         |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| **A. 런처 intent 선언 (제안)**   | manifest `<queries>`에 `MAIN`/`LAUNCHER` intent를 한 번 선언 → 아이콘이 있는 앱을 볼 수 있음. 코드는 **서버가 보낸 후보만** 확인 | 앱 업데이트 없이 새 앱도 확인. `QUERY_ALL_PACKAGES` 권한은 안 씀. **Play 심사에서 문제없는지 앱 팀 확인 필요** |
| B. 패키지 이름을 manifest에 적기 | 처음 지도(seed) 앱 10~20개를 `<queries><package>`로 적음                                                                         | 정책상 가장 깔끔. 새로 배운 앱은 다음 앱 업데이트 전까지 확인 불가                                             |
| C. 확인하지 않고 열어 보기       | 후보 순서대로 열어 보고, 안 열리면(`ActivityNotFoundException`) 다음 후보                                                        | 볼 권한 없이 됨. 앱이 실제로 열려 버려 조용히 확인할 수 없음 → 열기 직전에만                                   |

- **제안**: A. A가 정책상 어려우면 B + C (seed 앱은 조용히 확인, 새로 배운 앱은 열기 단계에서 확인)
- 고령자 앱은 접근성 서비스로 동작한다. 접근성 서비스에 이 제한이 다르게 걸리는지는 확인하지 못했다 → 앱 팀이 실제 기기에서 `getPackageInfo`를 한 번 시험
- 기기 사용 기록 권한(`PACKAGE_USAGE_STATS`)은 쓰지 않는다. 습관은 서버의 끝난 명령 기록으로 정함 (4.3)

### 4.5 슬롯 (말 속의 값)

jev는 고르기만 하므로 "임영웅", "김철수" 같은 값은 뽑지 못한다.

- 앱 IntentParser가 보내는 `slots`를 그대로 쓴다
- 목표에 필요한 슬롯이 비어 있으면 지도 안내를 하지 않고 Claude가 안내한다 (Claude가 말에서 값을 읽음)

## 5. 안내

### 5.1 명령 시작 때 한 번 (#17 classify)

```
#17 POST /v1/elder/classify
요청 { commandId, utterance, ruleLevel, ruleApp, signals[], slots? }
응답 { commandId, intent, app, sensitivity: {…},
       route?: {                                                                              ← 추가
         role: "music", ask: false,                 // ask: 민감한 역할이면 폰이 깔린 후보 중에서 물음
         candidates: [                              // 순서대로. 폰은 깔린 첫 번째를 씀 (4.3)
           { appId: "melon", packages: ["com.iloen.melon"], name: "멜론",
             goalId: "melon.open", goalVersion: 1, level: "L0", by: "pref" },
           { appId: "youtube", packages: ["com.google.android.youtube"], name: "유튜브",
             goalId: "youtube.search", goalVersion: 2, level: "L0", by: "default" } ],
         named: false,                              // 말한 앱이 분명함 → 후보 하나, 없으면 설치를 물음
         confidence: { app: 0.44, role: 0.81 } },
       clarify?: { kind: "intent" | "goal", say, options } }                                   ← 추가
```

- S4 classify가 아직 없으므로 이 구조로 만든다: **jev 성공이면 민감도는 목표 값**(`max(ruleLevel, 목표 level)`, signals 보정은 그대로), 실패면 Claude 분류 (서버 기획 5.2). 후보마다 목표가 달라 민감도가 다를 수 있으므로 후보마다 `level`을 주고, 응답의 `sensitivity`는 후보 중 가장 높은 값으로 한다
- `clarify`의 답은 같은 `commandId`로 classify를 다시 부를 때 `userReply`로 보낸다 → 서버가 route를 확정한다. 앱을 고르는 질문(민감한 역할)은 폰이 깔린 후보로 직접 묻고 결과를 guide의 `appId`로 알린다
- `commandId`는 앱이 명령 하나마다 만드는 값. 이 명령의 guide 요청·끝 신호가 모두 같은 값을 쓴다
- 서버는 `commandId`로 route(후보 전체)를 저장해 둔다 (`CMD#<commandId>`, TTL 1일). 앱은 고른 `appId`만 알려 주면 된다

### 5.2 화면마다 (#16 guide)

```
#16 POST /v1/elder/guide
요청 { …지금 필드…, commandId?, appId?, lastTap? }   ← 추가 (appId: 폰이 고른 후보 4.3, lastTap: 바로 앞 화면에서 실제 누른 노드 { text } 3.6)
응답 { …지금 필드…, source?: "map" | "ai" }   ← 추가 (앱 동작은 같음, 디버그·측정용)
```

`commandId`로 route를 찾고 `appId`로 후보 하나를 정한 뒤 (없으면 첫 번째 후보):

1. route 없음, 목표가 `verified` 아님, 기능 스위치 꺼짐 → **Claude** (지금과 같음, 프롬프트에 route의 목표 설명을 넣어 "하려는 일"을 분명히 함)
2. 지금 화면을 페이지로 맞춘다 (`match@v1`). `exact`·`similar`가 아니면 → Claude
3. 지금 페이지가 목표의 `arrive`면 → `finish`의 다음 단계로 안내
4. 아니면 지금 페이지에서 `arrive`까지 **`verified` 연결선만으로 가장 짧은 길**을 찾는다 (페이지 수십~수백 개라 메모리에서 바로 됨). 없으면 → Claude
5. 길의 첫 연결선 `targetText`를 지금 화면에서 찾는다. 못 찾으면 → Claude
6. 찾으면 **지도 안내**: 그 연결선의 행동·말로 응답한다 (슬롯 채움, 노드 번호는 지금 화면 것). Claude 응답과 **같은 모양**이라 앱은 바꿀 것이 없다
7. `finish`의 멈춤 단계(`stopAt`)면 지금 규칙대로 `stopped`로 응답한다

- 시작 화면이 어디든(설정 홈이든 디스플레이 화면이든) 그 자리에서 길을 찾으므로 시작 화면마다 길을 따로 둘 필요가 없다
- 지도 안내 중 한 번이라도 Claude로 넘어가면 그 명령은 그 뒤로 Claude가 안내한다 (오락가락하지 않게)
- 연결선을 따라 눌렀는데 다음 화면이 `to`와 다르면 그 연결선의 실패로 센다 (8.3)

**한 단계씩 준다 (결정)**. 길 전체를 한 번에 폰에 보내지 않는다. 화면이 바뀔 때마다 앱이 guide를 부르고, 서버가 지도에서 다음 한 단계를 찾아 준다. 지금 Claude 안내와 같은 흐름이라 앱은 바꿀 것이 없다.

|                                           | **한 단계씩 (이 문서)**                                                                      | 길 전체를 한 번에                                                                                       |
| ----------------------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 화면당 시간                               | 네트워크 왕복만 (Claude 없음). Lambda가 데워져 있으면 0.1~0.3초 정도로 예상 (아직 재지 않음) | 거의 0초                                                                                                |
| 앱이 할 일                                | 없음                                                                                         | 페이지 맞추기(`match@v1`)를 폰에도 만들어야 함 → 서버(TS)·앱(Kotlin) 두 곳에서 같은 규칙을 맞춰 가야 함 |
| 길에서 벗어날 때, 다른 화면에서 시작할 때 | 서버가 바로 알고 지금 페이지에서 길을 다시 찾거나 Claude로 넘김                              | 폰이 알아채고 서버를 불러야 함                                                                          |
| 멈춤 규칙 (송금·설치 확인)                | 서버가 지킴                                                                                  | 폰도 지켜야 함                                                                                          |
| 지도 학습 기록 (8장)                      | 단계마다 서버에 남음                                                                         | 끝날 때 폰이 몰아서 보내야 함                                                                           |
| 지도가 바뀔 때                            | 바로 반영                                                                                    | 이미 받은 길은 낡은 채로 진행                                                                           |

- 지도 안내는 LLM을 부르지 않으므로 화면당 시간이 지금 Claude 안내(1.8~4.1초)의 10분의 1 아래로 줄 것으로 본다. 판단(페이지 맞추기·벗어남·멈춤·학습 기록)이 서버 한 곳에 모인다
- **R4에서 화면당 시간을 잰다**. 느리면 **미리 보기**를 더한다: 응답에 다음 1~2단계(예상 페이지와 `targetText`)를 실어 보내고, 폰은 다음 화면에서 그 `targetText`가 보이면 서버를 기다리지 않고 바로 표시한다. 동시에 서버에도 보내서 서버가 확인·기록한다. 페이지 맞추기를 폰에 옮기지 않고 기다림만 줄이는 방법

| 필요              | 지금 main                        | 바꿀 것                                                                                         |
| ----------------- | -------------------------------- | ----------------------------------------------------------------------------------------------- |

| 끝났다는 신호     | 없음                             | 새 API `POST /v1/elder/commands/{commandId}/end` `{ result: "done" \| "gave_up" \| "stopped" }` |
| 기록 남기기       | **dev에만** 디버그 저장소에 남김 | prod에도 남김 (가림 적용, 화면·응답·페이지·출처). 보관 기간 정함 (12장)                         |

## 7. Opus 검토

### 7.1 언제

- 끝 신호 `done`이 오면 명령을 대기열(SQS)에 넣고, 별도 Lambda(`review-fn`)가 처리한다. 어르신 안내와 상관없이 돈다
- `gave_up`·`stopped`·`unknown`은 지도에 더하지 않는다. 다만 지도 안내 중에 일어났다면 쓴 연결선의 실패로 센다 (8.3)
- Claude가 안내한 명령만이 아니라 **지도 안내 명령도 일부 뽑아 검토**한다 (길이 아직 맞는지)

### 7.2 Opus에게 주는 것과 받는 것

- 입력: 어르신 말(가림), 그 앱의 지도 목표 목록, 단계마다 (가린 화면 노드, 페이지, 안내 응답, 출처), 끝 신호
- 화면 글자는 데이터로만 다룬다 (화면 속 지시를 따르지 않음 — guide 프롬프트와 같은 규칙)
- 출력 (구조화): 길을 **이동(연결선)**과 **이 목표만의 끝 단계**로 나눠서 낸다

```ts
{
  success: "yes" | "no" | "unsure",
  evidence: "마지막 화면에 밝기 막대가 왼쪽으로 옮겨져 있음",
  goal: { existing: "settings.brightness_down" } | { new: { app, name, desc, slots, level, category } },
  moves: [ { step: 0, action: "tap", targetText: "디스플레이" }, { step: 1, action: "tap", targetText: "밝기" } ],  // 돌아간 단계는 뺌
  finish: [ { step: 2, action: "swipe_left", targetText: "밝기", say: "…" } ],
  sensitiveSteps: [],                       // 송금·결제·인증·설치·권한·보내기
  personalText: false,                      // 슬롯으로 못 바꾼 개인 글자가 남았나
}
```

### 7.3 서버가 다시 확인하는 것 (Opus를 그대로 믿지 않음)

- `success`가 `yes`가 아니면 버린다
- 새 목표면 **jev로 중복 검사**: 새 목표 `desc`와 명령의 말을 기존 목표 후보로 jev에 물어, 기존 목표가 0.7 이상이면 새로 만들지 않고 그 목표에 합친다. 새 앱이면 기존 역할 중 하나로 넣거나(jev로 고름) 새 역할을 후보로 만든다
- 앱 자체에 대한 목표(깔기·업데이트·지우기)가 그 앱의 목표로 들어오면 Play 스토어 목표로 옮긴다 (3.4)
- 민감도는 `max(규칙 판정, Opus 제안)`. Opus가 내릴 수 없다
- 각 단계의 `targetText`가 실제 기록된 화면에 있었는지, 출발·도착 페이지가 `match@v1`로 맞는지 확인한다. 연결선은 기록된 (출발 페이지, 도착 페이지) 쌍으로 만든다
- `personalText`가 `true`이거나 슬롯 자리 밖에 숫자·이름처럼 보이는 글자가 있으면 버린다

## 8. 지도에 반영하는 규칙

### 8.1 후보 → 검증됨

- 새 목표·새 연결선은 `candidate`로 들어간다. candidate로는 **안내하지 않는다**
- **연결선**: 어느 목표에서든 같은 연결선(출발·도착 페이지 + `targetText`)이 **서로 다른 어르신 2명 이상**에게서 성공하면 `verified`
- **dev**: 쓰는 사람이 팀원 몇 명뿐이라 어르신 2명 기준을 채우기 어렵다 → dev에서는 **서로 다른 기기 2대**로 본다. prod는 어르신 2명
- **목표의 끝 단계**: 그 목표에서 같은 `finish`가 서로 다른 어르신 2명 이상에게서 성공하면 `verified`
- 연결선은 여러 목표가 같이 쓰므로 목표마다 처음부터 모을 때보다 검증이 빨리 쌓인다

### 8.2 자동으로 넣지 않는 것

| 경우                                                                    | 처리                                      |
| ----------------------------------------------------------------------- | ----------------------------------------- |
| 목표 민감도 L2 이상, 또는 끝 단계에 송금·결제·본인인증·설치·권한·보내기 | **사람 승인** 대기 (디버그 뷰어에서 승인) |
| 금융 앱(은행·증권·카드), 사기 의심 신호가 있던 명령                     | 지도에 넣지 않음                          |
| 앱 밖 웹 주소로 이어지는 길, 설치 앱이 아닌 패키지                      | 지도에 넣지 않음                          |

- 민감한 행동은 목표의 `finish`에 있으므로, 연결선을 같이 써도 멈춤 규칙은 목표 단위로 그대로 걸린다
- 승인된 민감 목표도 지도 안내는 **멈춤 단계에서 `stopped`로 끝난다** (지금 safety 규칙과 같음)

### 8.3 낡은 길 내리기

- 연결선을 따라 눌렀는데 도착 페이지가 다르거나, 지도 안내 중 Claude로 넘어가거나, `gave_up`·`stopped`(멈춤 단계 아님)로 끝나면 쓴 연결선·끝 단계의 실패로 센다
- 최근 20번 중 실패가 30%를 넘으면 `candidate`로 내린다 (다시 성공이 쌓이면 올라감)
- 앱 버전이 바뀌어 페이지가 안 맞으면 자연스럽게 Claude로 넘어간다. 새 버전에서 성공한 연결선이 새로 쌓인다
- 90일 동안 안 쓰인 연결선은 `retired`

| R5   | 자동 반영 켜기 (8장 규칙), 낡은 연결선 내리기, 뷰어 승인 화면                                                                                                                            | 지도 안내 비율·실패율             |
| R6   | 고령자 앱 연동 (`commandId`, 끝 신호, 후보 중 깔린 첫 번째 고르기·설치 확인(4.4), `clarify`). 문서 `docs/api/s4-classify.md`. 실제 말로 기준값 조정                                      | 실제 폰                           |

R3에서 반영 없이 먼저 재는 이유: Opus 판정이 틀리면 **틀린 길이 여러 어르신에게 퍼진다**.

## 12. 정할 것

1. **민감한 목표(L2 이상)**: 사람 승인으로 넣을지(이 문서의 제안), 자동 반영에서 아예 뺄지
2. **검증 기준**: 서로 다른 어르신 몇 명이 성공해야 `verified`인지 (제안: prod 어르신 2명, dev 기기 2대)
3. **prod 기록**: 가린 안내 기록을 prod에도 남겨도 되는지, 보관 기간(제안: 30일), 어르신 동의 문구
4. **고령자 앱 변경 요청**: `commandId`, 끝 신호, `lastTap`(실제 누른 노드, 3.6), 후보 중 깔린 첫 번째 고르기·말한 앱이 없을 때 설치 묻기·민감 역할 묻기(4.3), 설치 확인 방법 A/B/C(4.4: Play 정책, 접근성 서비스에서 실제로 되는지), `clarify` 처리. 앱 IntentParser goal 코드(`GOV24`, `YOUTUBE` …)와 지도 목표 id를 어떻게 맞출지
5. **역할 기본 앱**: 처음 기본값(예: 음악 → 유튜브)을 누가 정하고, 보호자 앱에서 바꿀 수 있게 할지
6. **외부 전송 동의**: 어르신 말이 OpenRouter·TypeSafe로 나가는 것을 허용할지, ZDR 설정 가능 여부
7. **OpenRouter 계정·결제**: 개인 키로 시험함. 팀 계정과 사용 한도
8. **보호자 권한을 목표 단위로**: 보호자 앱이 "정부24 등본은 알림만, 은행 송금은 승인" 같은 설정을 할지 (S4·S3과 함께)
9. **서버 기획 9장(캐싱)**: 이 문서의 지도 안내가 9장 캐싱을 대신하는지, 따로 두는지

v0.2:

- 카탈로그 → **데이터로 된 지도** (역할·앱·목표·연결선), 목표마다 id·버전
- **Opus 검토로 지도가 저절로 자람** (후보 → 서로 다른 어르신 2명 성공 → 검증됨, 민감 목표는 사람 승인)
- 캐시 대신 **지도 안내 모드**: 지금 페이지에서 목표 도착지까지 검증된 연결선으로 길 찾기
- **목표 = 도착지 + 끝 단계, 이동은 모든 목표가 같이 쓰는 연결선** (밝게/어둡게처럼 결과는 다르고 길은 같은 목표)
- 고르기는 **앱 → 목표 2단계로 확정** (목표 질문엔 고른 앱의 목표만), 큰 목록 시험(2.2)
- **역할**로 같은 일을 하는 앱을 묶고(한 앱이 여러 역할 가능), 역할 합계로 판정
- 앱 자체에 대한 일(깔기·업데이트·지우기)은 Play 스토어 목표
- **서버는 후보 앱 순서만 보내고 폰이 깔린 첫 번째를 고름** (설치 앱 목록은 폰 밖으로 안 나감). 순서는 습관 → 기본 앱 → jev 확률. **말한 앱이 분명하면 그 앱만**, 없으면 설치를 물음. 민감 역할은 깔린 후보 중에서 물음 (2.3 시험: 99.6%)
- route는 서버가 `commandId`로 저장. 기록·끝 신호·선호 저장 추가
- **지도는 실제 사용으로만 자람** (3.6). 팀 녹화는 시연용·사람 승인. guide에 `lastTap`(실제 누른 노드), dev 검증 기준은 기기 2대
