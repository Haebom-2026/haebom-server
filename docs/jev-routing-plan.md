# jev 앱·목표 라우팅 기획 (초안 v0.1)

- 작성일: 2026-11-26
- 상태: **기획**. 구현 전. 9장(캐시)은 사용자 캐싱 설계를 받으면 맞춰 고친다
- 관련: [서버 기획](server-plan.md) 5.2 classify·5.3 guide·9장 캐싱·12.7.1 화면 매칭, [S5 guide API](api/s5-guide.md)

## 0. 한 줄 요약

어르신의 말을 **jev(고르기 전용 모델)로 "어느 앱의 어느 목표"인지 먼저 고르고**, 고르기에 성공하면 그 (앱, 목표)를 캐시 키·민감도·안내의 기준으로 쓴다. 고르지 못하면(해당 없음, 확신 부족) 지금처럼 Claude가 처리한다.

```
어르신 말 ──▶ jev: 앱? 목표? ──성공──▶ route = (앱, 목표)
                    │                     ├─ 민감도: 목표에 적힌 단계 (S4)
                    │                     └─ 화면마다: (앱, 목표, 페이지) 캐시 ─hit→ 안내
                    │                                                    └miss→ Claude guide
                    └─실패(해당 없음·애매함)──▶ 지금 흐름 그대로 (Claude)
```

## 1. 왜 하나

| 문제                                                                                                   | jev가 푸는 방법                                                                       |
| ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| Sonnet guide는 요청마다 약 $0.0055(캐시 없으면 약 $0.02), 1.8~4.1초                                    | 캐시가 맞는 요청은 Claude를 부르지 않음                                               |
| 어르신 말이 제각각이라 캐시 키로 못 씀 ("등본 떼 줘" / "주민등록 등본 발급 받고 싶어" / "정부24 등본") | jev가 모두 `gov24 / resident_copy` 하나로 모음 → 키가 (앱, 목표, 페이지)로 단순해짐   |
| 민감도(S4)를 말마다 LLM으로 판단하면 느리고 흔들림                                                     | 목표마다 민감도를 미리 적어 둠. 보호자 권한도 목표 단위로 걸 수 있음                  |
| 글을 만드는 모델은 엉뚱한 값을 낼 수 있음                                                              | jev는 **목록 안에서 고르기만** 하고 후보별 확률을 줌 → 애매하면 확실하게 넘길 수 있음 |

## 2. jev 시험 결과 (2026-11-26)

OpenRouter Decisions API(`POST /api/alpha/decisions`, 모델 `typesafe/jev-1.14`, `choice` 질문). 말 64개(실제 폰 요청 24 + 직접 쓴 40, 해당 없음 7개 포함), 앱 11개·목표 5개 앱.

| 시험                        | 그대로 쓸 때             | 기준을 두면                                       |
| --------------------------- | ------------------------ | ------------------------------------------------- |
| A. 말 → 앱                  | 98% (63/64)              | 1등 ≥ 0.5: 97% 받아들임, 그중 **100%** 정확       |
| B. 말 + 앱 → 목표           | 98% (42/43)              | 1등 ≥ 0.7·차이 ≥ 0.3: 93% 받아들임, 그중 **100%** |
| C. 화면 + 할 일 → 누를 노드 | 42% (Claude와 같은 버튼) | 1등 ≥ 0.9: 18%만 받아들임 → **쓰지 않음**         |

- 속도: 중앙값 0.53초, 최대 0.76초. 비용: 호출당 약 $0.00004 (입력 100만 토큰당 $0.042, 출력 $0)
- 틀린 것: "박지성 찾아 줘" → 연락처(0.38, 기준 미달로 넘어감), "손주가 보던 영상 보고 싶어" → 유튜브 검색(0.57, 기준 미달로 넘어감)
- 겹치기 쉬운 쌍(등본/초본, 연락처 저장/전화 걸기/카톡 친구 추가, 사진 보기/찍기, 유튜브 검색/그냥 틀기)과 목록에 없는 말 7개는 모두 맞힘
- 한계: 말 40개는 직접 쓴 문장. 앱 연동 뒤 실제 말로 다시 잰다 (8장)

→ **앱·목표 고르기(A·B)에만 쓴다.** 화면에서 누를 버튼은 캐시의 `targetText` 또는 Claude가 정한다.

## 3. 카탈로그 (후보 목록)

jev 정확도는 후보 목록 품질이 정한다. 목록은 저장소에 코드로 두고 버전을 붙인다 (`catalog@v1`, 캐시 키에 포함).

### 3.1 모양

```ts
// src/route/catalog.ts (제안)
{
  version: "catalog@v1",
  apps: {
    gov24: {
      name: "정부24",
      desc: "공공 서류 발급(주민등록등본·초본, 가족관계증명서), 민원 신청",
      packages: ["kr.go.minwon.m"],
      goals: {
        resident_copy: {
          desc: "주민등록표 등본 발급 (같이 사는 가족이 나오는 서류)",
          level: "L2", category: "public",        // S4 민감도
          approvalAction: "guide_gov24_auth",     // S3 승인 action (있으면)
          slots: [],                              // 필요한 값 (없으면 [])
          cacheable: true,
        },
        resident_abstract: { desc: "주민등록표 초본 발급 (주소가 바뀐 기록이 나오는 서류)", … },
        open: { desc: "정부24를 열기만 함 (할 일은 아직 말하지 않음)", … },
      },
    },
    youtube: { goals: { search: { slots: ["query"], … }, open: { … } } },
    …
    none: { desc: "위 앱 어느 것에도 맞지 않는 일, 또는 무엇을 하려는지 알 수 없음" },
  },
}
```

- 모든 질문에 **`none`(해당 없음)** 후보를 넣는다. 고르기 모델은 맞는 답이 없어도 무언가를 고르기 때문
- 목표가 없는 앱(갤러리, 카메라 등)은 앱만 고른다 → 목표는 `open` 하나로 본다

### 3.2 중복을 없애는 규칙

| 겹침                  | 예                                | 처리                                                                             |
| --------------------- | --------------------------------- | -------------------------------------------------------------------------------- |
| 같은 뜻, 이름만 다름  | 등본 발급 / 등본 떼기 / 등본 출력 | **하나로 합침**. 다른 이름은 `desc`·예시에 넣음                                  |
| 비슷하지만 정말 다름  | 등본 / 초본, 송금 / 잔액 조회     | 남기고 `desc`에 **차이를 만드는 말**을 적음. 그래도 애매하면 어르신께 물음 (4.2) |
| 화면 흐름이 같은 목표 | 등본 PDF 받기 / 등본 우편 신청    | 결과 단위로 하나로 합침 (갈림은 화면에서 어르신이 고름)                          |

- 목록을 바꿀 때마다 **유사도 검사**(후보끼리 jev 점수)와 **혼동표**(회귀 말 세트에서 1·2등이 자주 붙는 쌍)를 돌린다 (`scripts/route-eval.ts`, 8장)
- 처음 범위: 시연 앱(정부24, 유튜브, 연락처, 전화, 설정, 갤러리, 카메라, Play 스토어, 카카오톡, 카카오T) × 목표 2~6개. Claude로 넘어간 말 로그를 보고 자주 나오는 목표를 더한다

## 4. 판정

### 4.1 호출 한 번에 앱·목표를 함께

목표 질문은 앱에 따라 다르지만, 한 번에 묻기 위해 **앱 질문 + 목표가 있는 앱마다 목표 질문**을 한 요청에 넣고, 고른 앱의 목표 질문 답만 쓴다. 질문이 늘어도 입력 토큰만 늘고 비용은 호출당 $0.0001 안쪽이다. (시험은 정답 앱의 목표만 물었으므로, 이 방식의 정확도·속도는 R1에서 다시 잰다.)

```json
{
  "model": "typesafe/jev-1.14",
  "state": "어르신이 한 말: 등본 떼 줘",
  "questions": {
    "app":   { "type": "choice", "instructions": "…", "criteria": { "gov24": "…", "youtube": "…", "none": "…" } },
    "gov24": { "type": "choice", "instructions": "…", "criteria": { "resident_copy": "…", "resident_abstract": "…", "none": "…" } },
    "youtube": { … }
  }
}
```

### 4.2 받아들이는 기준 (시작값, 8장에서 조정)

| 결과                                                                 | 처리                                                                                                  |
| -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 앱 `none`, 또는 앱 1등 < 0.5                                         | **실패** → 지금 흐름 (Claude)                                                                         |
| 목표 1등 ≥ 0.7 이고 1·2등 차이 ≥ 0.3, `none` 아님                    | **성공** → route = (앱, 목표)                                                                         |
| 목표 1·2등이 둘 다 0.3 이상이고 차이 < 0.3 (예: 등본 0.5 / 초본 0.4) | **어르신께 물음**: `ask` + `options` ["등본", "초본"]. 답을 받으면 그 목표로 확정. Claude 부르지 않음 |
| 그 밖 (목표 `none`, 1등 < 0.7)                                       | route = (앱, 목표 없음). 앱만 확정, 안내는 Claude                                                     |
| jev 오류·1.5초 초과                                                  | **실패** → 지금 흐름. jev 장애가 안내를 막지 않음                                                     |

### 4.3 슬롯 (말 속의 값)

jev는 고르기만 하므로 "임영웅", "김철수", "다음 주 토요일" 같은 값은 뽑지 못한다.

- 앱 IntentParser가 보내는 `slots`를 그대로 쓴다
- 목표에 필요한 슬롯(`slots: ["query"]`)이 비어 있으면 그 목표는 캐시를 쓰지 않고 Claude가 안내한다 (Claude가 말에서 값을 읽음)

## 5. 어디에 붙나

### 5.1 명령 시작 때 한 번 (#17 classify)

route는 명령 하나에 한 번만 정한다. 화면이 바뀔 때마다 부르는 guide(#16)에서 매번 jev를 부르지 않는다.

```
#17 POST /v1/elder/classify
요청 { commandId, utterance, ruleLevel, ruleApp, signals[], slots? }
응답 { commandId, intent, app, sensitivity: {…},
       route?: { catalog: "catalog@v1", app: "gov24", goal: "resident_copy",
                 confidence: { app: 0.98, goal: 0.93 } } }   ← 추가
```

- S4 classify가 아직 없으므로, S4를 이 구조로 만든다: **jev 성공이면 민감도는 카탈로그 값**(`max(ruleLevel, 목표 level)`, signals 보정은 그대로), 실패면 Claude 분류 (서버 기획 5.2)
- jev가 "어르신께 물음"(4.2)이면 classify 응답에 `clarify: { say, options }`를 실어 앱이 바로 묻게 한다

### 5.2 화면마다 (#16 guide)

```
#16 POST /v1/elder/guide
요청 { …지금 필드…, route?: { catalog, app, goal } }   ← 추가 (classify 응답을 그대로 실어 보냄)
```

- `route`가 있으면 캐시 키로 쓴다 (6장). 없으면 지금과 같다
- Claude 프롬프트에도 route를 넣어 "하려는 일"을 분명히 한다 (goal 코드보다 정확)
- 서버는 route 값을 카탈로그에 있는지 확인하고, 없거나 버전이 다르면 무시한다

## 6. 캐시와 연결 (S6, 제안 — 사용자 설계로 교체)

```
키   = catalog 버전 + prompt 버전 + 앱 + 목표 + 페이지(match@v1 pageId) + 단계(history 길이 구간)
값   = { type, targetText, dir, seekText, say, status }   ← 노드 번호는 저장하지 않음
```

- **hit여도 다시 확인**: 지금 화면에서 `targetText` 노드를 찾아 번호를 정한다. 못 찾으면 버리고 Claude
- 페이지 판정이 `ambiguous`·`new`면 miss
- **저장하지 않음**: `stopped`·`clarify`·`off_track` 응답, 금융·본인인증 목표(`cacheable: false`), 비밀번호 화면, `targetText`에 개인 글자(연락처 이름, 검색어 결과 제목)가 든 응답
- 범위: 전역(모든 어르신 공유)으로 시작하되, 개인 글자가 든 답은 저장하지 않는 규칙으로 막는다
- 메트릭: route 성공률, 캐시 적중률, 아낀 Claude 호출 수·비용

## 8. 측정

- **회귀 말 세트**: 이번 시험의 말 64개 + 정답을 `test/fixtures/route-utterances.json`으로 저장소에 둔다. 실제 앱 연동 뒤 들어온 말을 정답 붙여 계속 더한다
- **`scripts/route-eval.ts`**: 세트를 jev에 돌려 정확도, 기준별 받아들임·정확도, 혼동표, 지연, 비용을 낸다. 카탈로그나 기준값을 바꿀 때마다 돌린다 (돈이 드는 외부 호출이라 CI에서는 돌리지 않음)
- **목표**: 받아들인 것 중 정확도 ≥ 99%, 받아들임 ≥ 80%. 못 미치면 기준을 올려 정확도를 지킨다 (틀린 route는 엉뚱한 안내·민감도로 이어지므로)

## 10. 정할 것

1. **카탈로그 관리 주체**: 서버(저장소 코드)로 시작. 고령자 앱 IntentParser의 goal 코드(`GOV24`, `YOUTUBE` …)와 어떻게 맞출지
2. **route를 누가 들고 다니나**: 앱이 classify 응답을 guide에 실어 보냄(제안) vs 서버가 `commandId`로 저장해 두고 찾음
3. **캐시 범위·키**: 사용자 캐싱 설계와 맞춤 (6장)
4. **외부 전송 동의**: 어르신 말이 OpenRouter·TypeSafe로 나가는 것을 시연·서비스에서 허용할지, ZDR 설정 가능 여부
5. **OpenRouter 계정·결제**: 개인 키로 시험함. 팀 계정과 사용 한도
6. **보호자 권한을 목표 단위로**: 보호자 앱이 "정부24 등본은 알림만, 은행 송금은 승인" 같은 설정을 할지 (S4·S3과 함께)
