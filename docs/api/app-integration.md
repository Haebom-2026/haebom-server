# 고령자 앱 연동 안내 (jev 라우팅·지도 안내·지도 학습, R6)

- 작성일: 2026-11-27
- 대상: 고령자 앱
- 상태: 서버 **dev 배포 완료** (R1~R5). 앱 연동 전
- 자세한 계약: [S4 classify·앱 선택·끝 신호](s4-classify.md), [S5 guide](s5-guide.md). 서버 설계: [jev 라우팅 기획](../jev-routing-plan.md)

이 문서는 흩어져 있는 내용을 **명령 하나의 흐름**으로 묶은 것입니다. 필드 하나하나의 규칙은 S4·S5가 기준입니다.

---

## 1. 왜 해야 하나

앱이 아래 네 가지를 보내 주면 서버가 할 수 있는 일이 늘어납니다. 보내지 않아도 지금처럼 Claude가 안내합니다 (깨지는 것 없음).

| 앱이 보내는 것                                    | 서버가 하는 일                                                                                                                                      |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| classify 응답의 후보 중 **고른 앱** (앱 선택 API) | 명령에 앱·목표를 고정. 목표의 민감도로 단계를 올림                                                                                                  |
| guide마다 `commandId`·`lastAction`·`deviceId`     | **지도 안내**: 검증된 길이 있으면 Claude 없이 한 단계씩 (화면당 약 0.6초, Claude는 약 3초). 지도에 없거나 조금이라도 다르면 그 명령은 끝까지 Claude |
| 명령이 끝나면 **끝 신호**(마지막 화면 포함)       | **지도 학습**: Opus가 성공한 안내를 검토 → 서로 다른 **기기 2대**에서 성공한 길이 자동으로 지도에 들어감. 지도 안내가 실패하면 그 길을 내림         |
| `deviceId` (기기마다 고정된 값)                   | 학습의 "기기 2대" 기준. **없으면 그 명령은 지도에 반영되지 않습니다**                                                                               |

지금(dev)은 학습·지도 안내가 dev 서버에서만 켜져 있습니다. prod는 개인정보 정책이 정해질 때까지 jev 라우팅·기록이 꺼져 있고, 앱이 같은 필드를 보내도 무시합니다 (보내도 안전).

## 2. 명령 하나의 흐름

```
어르신 말
  │
  ├─ ① commandId 만들기
  ├─ ② POST /v1/elder/classify            → 단계(sensitivity), 후보 앱(route), 질문(clarify)
  ├─ ③ 후보 중 깔린 앱 고르기 (폰 안에서)
  ├─ ④ POST /v1/elder/commands/{id}/app   → 앱·목표 고정 (질문 답도 여기로)
  ├─ ⑤ POST /v1/elder/guide  (화면마다 반복, commandId·lastAction·deviceId 포함)
  │      응답의 stepId 를 기억 → 어르신이 그 안내대로 하면 다음 요청의 lastAction.stepId 로
  └─ ⑥ POST /v1/elder/commands/{id}/end   (끝나면 한 번, 마지막 화면·마지막 행동 포함)
```

### ① commandId

- 명령마다 새로 만드는 0 이상 정수. **같은 어르신이 하루 안에 다른 명령에 같은 번호를 쓰면 안 됩니다** (앱을 다시 깔아도 겹치지 않게 시각 기반을 권장, 예: 초 단위 Unix 시각)
- 같은 명령의 classify 재시도·앱 선택·guide·끝 신호는 모두 같은 번호를 씁니다

### ② classify

- 지금처럼 규칙 결과로 먼저 진행하고, 응답이 오면 **단계가 더 높을 때만** 반영 (4초 넘으면 무시)
- 응답에 `route`가 있으면 ③으로. 없으면(꺼짐·L3·사기 의심·`degraded`) 지금처럼 진행
- `clarify.questionId == "intent"`(하려는 일이 갈림)이면 먼저 어르신께 묻고 답을 ④로 보냄 → 응답의 `route`로 ③

### ③ 후보 고르기 (S4 4장, 기획 4.3·4.4)

`route.candidates`는 **순서가 매겨진 최대 3개**입니다. 판단은 서버가 했으니 앱은 순서대로 보기만 합니다.

| 경우                              | 앱이 할 일                                                                                                    |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| 깔린 후보가 있음                  | 순서대로 보고 **깔린 첫 번째** → ④ (`installState: "installed"`). 그 후보에 `clarify`가 있으면 묻고 답을 같이 |
| `ask: true` (은행·결제 같은 역할) | 순서대로 고르지 않고 **깔린 후보만** 보여 주고 물음 → ④에 `askedUser: true`                                   |
| `exclusive: true` 인데 안 깔림    | 다른 앱으로 바꾸지 않고 "○○이 없어요. 설치할까요?" (예면 **새 명령**으로 classify부터)                        |
| 하나도 안 깔림                    | 설치를 권함 (예면 새 명령)                                                                                    |
| 깔렸는지 **확인할 수 없음**       | 설치를 권하지 않음. 그 후보를 고른 것으로 ④ (`installState: "unknown"`)                                       |

- 설치 앱 목록은 폰 밖으로 보내지 않습니다. 후보의 `packages`만 확인합니다
- 안드로이드 11 이상은 볼 권한이 없으면 깔려 있어도 "없음"으로 나옵니다. manifest `<queries>`에 런처 intent(`MAIN`/`LAUNCHER`)를 선언하는 방법을 제안합니다 (기획 4.4, **Play 심사 확인은 앱 팀**). 접근성 서비스에서 다르게 동작하는지도 실제 기기로 확인 부탁드립니다

### ④ 앱 선택 API

```json
POST /v1/elder/commands/42/app
{ "appId": "settings", "installState": "installed", "askedUser": false }
```

- 응답의 `goal`이 그 명령의 목표, `sensitivity.level`이 올라갔으면 바로 반영
- 한 번 정한 앱은 바뀌지 않음 (다른 앱 409). 겹친 요청 409 → 다시 시도. jev 시간 초과 503 → 같은 요청 다시
- **이 단계를 건너뛰면 지도 안내가 일어나지 않습니다** (서버가 어느 목표인지 모름)

### ⑤ guide (화면마다)

S5 요청에 아래 세 필드를 더합니다.

```json
{
  "requestId": 3,
  "goal": "OPEN_APP",
  "utterance": "화면 좀 어둡게 해 줘",
  "screen": { "pkg": "com.android.settings", "width": 1080, "height": 2400, "nodes": [ … ] },
  "commandId": 42,
  "deviceId": "a1b2c3d4e5f6",
  "lastAction": { "stepId": "smwy00pxz5355f7", "seq": 1, "action": "tap", "text": "디스플레이" }
}
```

| 필드         | 규칙                                                                                                                                                 |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `commandId`  | ①의 번호                                                                                                                                             |
| `deviceId`   | 6장. 이 기기에서 늘 같은 값                                                                                                                          |
| `lastAction` | **앞 화면에서 어르신이 실제로 한 행동** (첫 요청엔 없음). 접근성 이벤트로 잡습니다                                                                   |
| ├ `stepId`   | 앞 화면에서 받은 응답의 `stepId`. **그 안내를 따랐을 때만** 넣습니다 (안내 없이 한 행동이면 뺌)                                                      |
| ├ `seq`      | 명령 안 행동 순번. 0부터 **빠짐없이** +1 (뒤로·홈 포함). 놓친 행동이 있으면 번호를 건너뛰어 주세요 → 그 구간은 학습하지 않습니다                     |
| ├ `action`   | `tap` `type` `swipe_up` `swipe_down` `swipe_left` `swipe_right` `back` `home` `other`. 밀기는 **손가락이 움직인 방향**                               |
| └ `text`     | 누른 요소의 글자: `t`가 비어 있지 않으면 `t`, 아니면 `d` (노드 직렬화와 같은 규칙). `type`이면 넣은 값을 보내지 않아도 됩니다 (서버도 저장하지 않음) |

**응답** (S5 3장과 같은 모양)

- `stepId`: 이 안내의 id. 어르신이 따르면 다음 요청의 `lastAction.stepId`로
- `source`: (dev에만) `map`(지도 안내) / `ai`(Claude). 표시용으로 쓰지 마세요 (로그·디버그용)
- 지도 안내도 `highlight`·`swipe`와 `status: "in_progress"`로 옵니다. **앱이 구분해서 처리할 것은 없습니다**
  - 문장은 틀로 만듭니다: `'디스플레이'를 눌러 주세요.`, `화면을 왼쪽으로 밀어 주세요.` (밀 곳이 하나뿐이면 `target`도)
- 같은 화면에서 다시 요청하면(네트워크 재시도·말 다시 하기) **같은 `stepId`의 같은 안내**가 올 수 있습니다. 새 안내로 다루지 말고 같은 단계로 보시면 됩니다 (두 번까지, 그 뒤엔 Claude가 이어 감)
- 지도 안내 중 Claude로 넘어가도 앱은 할 일이 없습니다 (응답 모양 같음)

### ⑥ 끝 신호

```json
POST /v1/elder/commands/42/end
{ "result": "done",
  "finalScreen": { "pkg": "com.android.settings", "width": 1080, "height": 2400, "nodes": [ … ] },
  "deviceId": "a1b2c3d4e5f6",
  "lastAction": { "stepId": "s…", "seq": 2, "action": "swipe_left", "text": "밝기 막대 80%" } }
```

| `result`       | 언제                                          | 학습                                   |
| -------------- | --------------------------------------------- | -------------------------------------- |
| `done`         | 어르신의 일이 끝남 (Claude가 `done`을 줌 등)  | Opus 검토 → 반영                       |
| `stopped_safe` | 송금·설치 확인 같은 멈춤 단계에서 바르게 멈춤 | Opus 검토 (사람 확인)                  |
| `stopped_user` | 어르신이 그만둠                               | 지도 안내 중이었으면 그 길의 실패로 셈 |
| `gave_up`      | 안내가 막혀 포기                              | 위와 같음                              |

- `done`·`stopped_safe`이면 **`finalScreen`을 꼭** 보내 주세요 (성공 판정의 근거, 없으면 학습하지 않음). 노드 형식은 guide와 같음
- `lastAction`: 마지막 guide 화면에서 한 마지막 행동 (다음 guide 요청이 없으니 여기에). `seq`는 이어서
- 한 번 정한 결과는 바뀌지 않음 (같은 결과 재전송 200, 다른 결과 409)
- 끝 신호를 못 보낸 명령은 학습되지 않을 뿐 문제는 없습니다

| ---------------------------------- | ------------------------- | --------------------------------------------------------- |

## 4. 지도 안내가 쓰이는 조건 (참고)

앱이 맞출 것은 없지만, 시험할 때 "왜 Claude가 안내했지?"를 이해하는 데 씁니다 (기획 5.4).

- 고른 목표가 지도에 **검증되어(verified)** 있고, 값이 필요한 목표(검색어 등)가 아님
- 지금 화면이 지도에 배운 화면과 **지문이 정확히 같음** (글자·위치·클래스·체크 상태. 숫자는 무시)
- 누를 글자가 화면에 하나뿐이고 입력 칸·꺼진 버튼·민감한 글자(설치·허용·결제·보내기 등)가 아님
- 고른 앱이나 홈 화면이고, 비밀번호 칸·금액이 보이는 화면이 아님
- 사기 의심·L3 명령이 아님
- 앞 지도 안내를 따랐다면(`lastAction.stepId`) 누른 글자·도착 화면이 지도와 같음

하나라도 아니면 그 명령은 끝까지 Claude가 안내합니다.

## 5. 오류·재시도

| API        | 응답                   | 앱 동작                                          |
| ---------- | ---------------------- | ------------------------------------------------ |
| classify   | 200 + `degraded: true` | 규칙 결과 유지                                   |
| classify   | 503 `unavailable`      | 규칙 결과로 진행 (재시도 선택)                   |
| 앱 선택    | 409 `conflict`         | 겹친 요청이면 다시 시도, 다른 앱이면 그대로 진행 |
| 앱 선택    | 503 `unavailable`      | 같은 요청 다시                                   |
| 앱 선택·끝 | 404                    | 지난 명령(하루 지남)·다른 어르신 것 → 버림       |
| guide      | 항상 200               | 실패도 `type: "say"`                             |
| 끝 신호    | 409                    | 이미 다른 결과로 끝남 → 버림                     |

## 6. deviceId

- 8~64자 `[A-Za-z0-9_-]`. **기기마다 고정**: 앱을 다시 실행해도 같은 값. 디버그 뷰어 하트비트에 쓰는 값과 같게 맞춰 주세요 (뷰어에서 같은 기기로 보임)
- 개인을 알아볼 수 있는 값(전화번호·IMEI)은 쓰지 마세요. 앱 설치 때 만든 무작위 id를 권합니다
- 서버는 이 값으로 "서로 다른 기기 2대에서 성공했나"를 셉니다. **없으면 uid 기반 가상 기기로 기록되고, 가상 기기 명령은 지도에 반영하지 않습니다** (같은 폰의 두 사람이 기기 2대로 세지 않게)
- 같은 기기를 여러 어르신이 쓰면 기기 1대로 셉니다

## 7. dev에서 확인하는 법

- 디버그 뷰어(<https://dv888sh4vt1v6.cloudfront.net>)의 기기 화면 목록에서 guide 기록을 열면, 지도로 안내한 화면은 "모델 호출 안 함: map"으로 보이고 기록 원본의 `map`에 판단(`step`·`resend`·`ai`와 Claude로 넘긴 이유)이 있습니다
- 서버 쪽 스크립트 (서버 팀): `scripts/map-pending.ts`(사람 확인 대기), `scripts/map-seed.ts`(사람 승인으로 넣기), `scripts/map-block.ts`(긴급 차단)
- 같은 명령을 **서로 다른 두 기기**에서 끝까지 하면(끝 신호 `done`), 세 번째부터 지도 안내가 나옵니다 (지도 캐시 때문에 최대 1분 뒤)

## 8. 앱 팀 할 일

- [ ] 명령마다 `commandId` 만들기 (하루 안 재사용 금지)
- [ ] classify 응답의 `route` 처리: 후보 순서대로 설치 확인(세 상태), `exclusive`·`ask`·`clarify`
- [ ] 앱 선택 API 호출 (질문 답 포함)
- [ ] 접근성 이벤트로 실제 행동 잡기 → `lastAction` (`stepId`는 따랐을 때만, `seq`는 빠짐없이)
- [ ] guide 응답의 `stepId` 기억, 같은 `stepId` 재응답은 같은 단계로
- [ ] guide·끝 신호에 `deviceId`
- [ ] 끝 신호 (결과 네 가지, `done`·`stopped_safe`면 마지막 화면)
- [ ] 설치 확인 방법 정하기 (`<queries>` 런처 intent, Play 심사)
